# Назначение файла — общие правила, не привязанные к проекту

Этот файл — источник общих правил для ИИ-агентов (Claude Code, DeepSeek Harness) во всех проектах,
которые используют эту WF-папку. Правила конкретного проекта живут в ветке проекта: `Client/CLAUDE.md`
(клиент) и `Server/CLAUDE.md` (сервер). Общее правило действует везде; проектное — только в своём
репозитории и только в своей области, и при конфликте уточняет общее, а не отменяет его молча.

# Где живут инструкции

Все файлы инструкций проекта (его `CLAUDE.md`, `AGENTS.md` и раскладка агентов: команды, скиллы,
документация, память) живут в WF-папке **вне контейнера** и правятся только там: у клиента это её
подпапка `Client` (у сервера — соседняя подпапка `Server`) в ветке проекта. Рабочий каталог
`/workspace/client` подключён к ней симлинками `CLAUDE.md`, `AGENTS.md`, `.claude/` и `.deepseek/`.

1. Проверка: `ls -l /workspace/client/CLAUDE.md /workspace/client/AGENTS.md /workspace/client/.claude
   /workspace/client/.deepseek` — все четыре ссылки ведут в папку инструкций клиента. Ссылки битые или
   на их месте обычные файлы — остановиться, ничего не создавать и не перезаписывать рядом (копия в
   контейнере теряется при пересоздании и расходится с источником), спросить Пользователя.
2. Ссылки в файлах инструкций — только относительные, от папки инструкций того репозитория, в котором
   лежит файл: `.claude/docs/<файл>.md` — файл в ней же, `../server/...` — соседняя папка инструкций
   сервера (в контейнере `/workspace/server`, в папке WF она называется `Server`). Абсолютных путей
   внутрь инструкций не записывать: в macOS путь начинается с `/Users/...`, в контейнере — с `/wf/...`,
   и в другом окружении такая ссылка не работает.
3. Правки — в папке инструкций, в том числе через контейнерные пути (`/workspace/client/CLAUDE.md`
   ведёт в тот же файл). Внешняя папка копий не держит: `.deepseek/` — зеркало, его обновляет
   конвертер, отдельных копий инструкций нет.
4. Правится только `CLAUDE.md` в папке инструкций, остальные файлы инструкций — через него и конвертер:
   `AGENTS.md` и `.deepseek/instructions/project.md` генерируются командой
   `python3 .deepseek/scripts/convert.py export` из рабочего каталога проекта. Корень конвертер берёт
   сам — на два уровня выше скрипта, то есть папку инструкций репозитория; `--repo` нужен, только если
   запускать копию скрипта из другого места.

# Язык общения

Все ответы ассистента пользователю должны быть на русском языке. Это касается ЛЮБЫХ агентов/
субагентов, запускаемых через Agent tool (Explore, general-purpose, Plan, кастомные агенты из
`.claude/agents/<команда>/*.md` и т.д.) — их финальные ответы пользователю тоже должны быть на русском.

# Явное указание личности: «Пользователь» или «ИИ»

Когда в тексте для человека (ответ ассистента, вопрос, документация, коммит, PR) или в передаче между
агентами речь идёт о личности, она называется прямо: «Пользователь» (живой человек, принимающий
решения) либо «ИИ» (ассистент: базовая сессия, любой агент системы, субагент). Неопределённые
местоимения «сам/сама/само/сами», «он/его/ему» без подлежащего, «кто-то» не использовать — по ним не
видно, о ком речь. Фразы, где «сам» выражает свойство объекта или кода («метод сам проверяет
предусловия», «сеттер сам увеличивает `styleID`»), правило не затрагивает. Подробно и для агентов —
`.claude/docs/agent-system-workflow.md#who-acts` в ветке проекта.

# Проверка на противоречие с ранее принятыми решениями

Прежде чем зафиксировать ответ пользователя как окончательное решение — сверься с уже принятыми
решениями по этой же области (память, документация, ГДД). Явное противоречие не принимать молча:
переспросить («Вы уверены? Ранее здесь было решено X, причина — Y; новое решение этому противоречит,
возможные последствия — Z») и продолжать только после повторного подтверждения. Это дополнительная
проверка поверх обычного вопроса пользователю, а не замена ему. Подробно — раздел «Проверка на
противоречие с ранее принятыми решениями» в `.claude/docs/agent-system-workflow.md` ветки проекта.

# Порядок вопросов пользователю

В один `AskUserQuestion` — только независимые вопросы. Если какой-то вариант ответа на один вопрос
снимает или меняет другой, этот другой задаётся отдельным вызовом после разбора ответа. Подробно и
для агентов — `.claude/docs/agent-system-workflow.md#question-order` в ветке проекта.

# Без развёрнутых комментариев в коде

Архитектурные пояснения (что за класс, почему так спроектировано, TODO) — в документации проекта
(`.claude/docs/<тема>.md`), не в исходниках. В коде — либо без комментария, либо одна строка
`// См. .claude/docs/<файл>.md#<якорь>`; короткие однострочные `//` с неочевидным WHY на месте
допустимы.

Ссылки на доки живут только на время разработки задачи. Когда пользователь сообщает о завершении
задачи, сначала финально обновляется и оптимизируется документация, затем все строки-ссылки
удаляются из кода области целиком.

# Многоагентная система разработки (команды агентов)

Типовая иерархия команд агентов — библиотекари → аналитики → разработчики плюс интеграция; раскладка
`agents/`, скиллы `skills/`, документация и память — в `.claude` клиента и сервера ветки проекта.
Устройство системы, контракты команд, правило «решение всегда за пользователем» — в
`.claude/docs/agent-system-workflow.md` ветки проекта; читать его целиком только когда решил(а)
входить в пайплайн (см. ниже) — не ради мелких задач. Состояние между сессиями (последняя ветка) — в
служебном `.claude/session_state.json` (НЕ часть memory-системы); у сервера свой независимый файл,
ветки трекаются раздельно.

## Проверка ветки/сессии при старте

В начале КАЖДОЙ по-настоящему новой сессии (свежий чат без предыдущего контекста в этом диалоге, а не
продолжение уже идущего разговора):

1. Прочитай `.claude/session_state.json` → `lastBranch`, сравни с текущей git-веткой этого
   репозитория. Если в этой же сессии затрагивается и второй репозиторий проекта — аналогично сверь
   его собственный `.claude/session_state.json` с его веткой.
2. Если текущая ветка ≠ основная ветка проекта И текущая ветка ≠ `lastBranch` (для затронутого
   репозитория) — это точно новая задача на новой ветке: прежде чем продолжать, уточни у пользователя
   тип задачи:
   - разработка полностью новой фичи;
   - расширение уже имеющейся фичи/компонента;
   - исправление бага в существующем компоненте.
3. Обнови `lastBranch` в соответствующем `.claude/session_state.json` на текущую ветку.

Если сохранённая ветка совпадает с текущей — это продолжение той же работы, повторно тип задачи не
уточняй.

## Когда вообще входить в пайплайн команд

Пайплайн (библиотекари → аналитики → разработчики) — не для любого запроса. Порог срабатывания НЕ
определяй сам автоматически по размеру/типу задачи — спрашивай пользователя явно каждый раз, когда
запрос похож на дев-задачу в игровом коде проекта, но неочевидно, разработка это, исследование или
мелкая правка: «делать через пайплайн команд или разобраться напрямую?» Однозначно НЕ спрашивай и
работай напрямую (без пайплайна) для: мелких точечных правок уровня опечатки/1 строки, вопросов «как
что-то устроено» без изменения кода, работы над самой инфраструктурой агентов (`.claude/*`,
`CLAUDE.md`) — она не является предметом этой системы, а её конфигурацией.

Входишь в пайплайн — читай `.claude/docs/agent-system-workflow.md` ветки проекта перед вызовом первого
агента.

## Контроль расхода токенов

При входе в пайплайн — если в этой сессии ещё нет активной почасовой проверки (сверь `CronList`),
создай её: `CronCreate` с `cron: "17 * * * *"`, `recurring: true`, промпт — запустить
`python3 .claude/scripts/token_usage_check.py 3600` из корня рабочего каталога, разобрать JSON:
- `idle: true` (за час не было ходов, кроме самой проверки, и работы субагентов) — пользователь
  отошёл: `CronList` → `CronDelete` этой задачи, ответ одной строкой «проверка токенов снята из-за
  простоя». При следующем сообщении пользователя пересоздать её (хук `token_check_resume_hook.py`
  напоминает об этом) — затем выполнить само сообщение.
- `flags` пуст — одна короткая строка «в норме», без деталей.
- `flags` непуст (ratio эффективного/нового input к output выше порога роли (10:1, у библиотекарей и
  integration — 25:1) у агента/сессии в целом, ИЛИ cache hit rate < 70% у агента с 2+ вызовами за
  час) — коротко перечислить, что превышено, и спросить через `AskUserQuestion`: оптимизировать сейчас
  или игнорировать. Без ответа пользователя дальше не действовать. Выбрано «оптимизировать» — новое
  правило сразу дописать одной строкой в `.claude/docs/agent-system-workflow.md#token-economy` ветки
  проекта (существующее — уточнить, не дублировать).

Ограничение: `CronCreate`-задачи живут только внутри текущей сессии (максимум 7 дней, исчезают при
закрытии чата) — при новой сессии, если снова входишь в пайплайн, создавай заново. Формулы метрик и
пороги — в самом скрипте (`.claude/scripts/token_usage_check.py`).

# Ветки этого репозитория и что где хранится

`main` — только общие правила (этот файл) и инфраструктура подключения (`tools/link_workspaces.py`);
проектные документы, архитектура, ГДД, агенты и память сюда не добавляются. Ветка проекта — `my_first_game`
(свои документы и инструкции); архив документации и архитектуры «Танков» — `tank-docs`. Работа над
проектными правилами идёт в ветке проекта, их `CLAUDE.md` — источник истины для этого проекта.
