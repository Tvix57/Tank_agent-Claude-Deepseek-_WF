# Документы игрового дизайна (ГДД)

Правила работы (создание, дополнение, проверка, связь с архитектурой) —
`/workspace/client/.claude/docs/agent-system-workflow.md#gdd`. Здесь — только соглашения и шаблон.

- Одна копия на client и server, файл `<область>-gdd.md` (имя области — как у архитектурного
  документа: `collections-gdd.md` ↔ `collections-architecture.md`).
- Только бизнес-логика (что и почему), без классов, методов и путей к коду.
- Каждый раздел — отдельное правило/механика со стабильным якорем `{#gdd-<раздел>}`; на якоря
  ссылаются архитектурные документы обеих сторон, поэтому якоря не переименовывать без обновления
  ссылок.
- Структура (список разделов) согласуется с пользователем ДО написания документа.

## Шаблон

```markdown
# <Область> — документ игрового дизайна

**Статус источника:** из файла пользователя (<имя файла>, <дата>) | черновик — по примерному описанию | черновик — по коду (правила из кода не подтверждены, они в #gdd-open)
**Архитектура:** client — `…/client/.claude/docs/<область>-architecture.md`;
server — `…/server/.claude/docs/<область>-architecture.md` (если есть)

**Содержание:** [Назначение](#gdd-purpose) · [<Раздел>](#gdd-<раздел>) · … ·
[Открытые вопросы](#gdd-open) · [Журнал изменений](#gdd-log)

## Назначение фичи {#gdd-purpose}
Зачем фича игроку и игре, 2–5 предложений.

## <Правило / механика> {#gdd-<раздел>}
Условия, числа, ограничения, граничные случаи, что видит игрок.

## Открытые вопросы {#gdd-open}
- <вопрос> — <где всплыл, дата>. Закрытый вопрос переносится в соответствующий раздел и удаляется
  отсюда.

## Журнал изменений {#gdd-log}
Только изменения уже описанной логики, одна строка на правку; новые разделы сюда не пишутся.
- <дата> — <раздел>: <было> → <стало>.
```
