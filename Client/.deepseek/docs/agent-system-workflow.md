# Многоагентная система разработки — полный workflow

Читается ТОЛЬКО когда базовая сессия уже решила входить в пайплайн — не грузи ради мелких правок.
`client`/`server` — два репозитория с независимыми командами (`client-*`/`server-*`), плюс общая
`integration-*` (идентичные копии в обоих). Серверный порядок под своими именами —
`/workspace/server/.claude/docs/agent-system-workflow.md`.

## Какую сторону выбрать {#side}

Чисто клиентская / чисто серверная / обе (новый API-контракт, обмен данными, баг на стыке "сервер
отдал не то / клиент принял не так"). Обе стороны — дополнительно `integration-lead` как точка
синхронизации (см. ниже).

## Порядок обращения к клиентским командам {#order}

1. **`client-librarian-lead`** — всегда первый. Спроси про компонент/область (для "новой фичи" — ещё и
   референсы), узнай у лида, есть ли документация/паттерны.
   - Новая фича без документации по компоненту — уточни референс(ы), запроси документацию по ним.
   - Нет документации нигде — шаг 2.
   - Документация нашлась — сразу к `client-developer-lead` (шаг 3) с этой документацией.
2. **`client-analyst-lead`** — когда документации нет. Запросит ТЗ/референс, проанализирует, создаст
   архитектуру, вернёт список аналитиков. Auto-create документацию делает СРАЗУ только если область
   сама не изменится в этой задаче — иначе откладывает до конца (одна полная версия вместо двух).
   **Модель:** первичный анализ новой области (документации нет, шаги 1–8 лида) — вызывай лида
   разово с `model: "fable"` в Agent tool. Все последующие вызовы (п.9 после разработки,
   уточнения, повторные сверки) — без параметра `model`, то есть на `opus` из frontmatter. Сам
   frontmatter лида не меняй.
3. **`client-developer-lead`** — получает архитектуру+список аналитиков (шаг 2) либо документацию
   (шаг 1). Определяет разработчиков, пишет код, передаёт саммари `client-analyst-lead`.

## Команда синхронизации client ↔ server {#integration}

`integration-lead` подключается ДОПОЛНИТЕЛЬНО, не вместо клиентских/серверных команд:
- **Анализ** — до фиксации архитектуры `*-analyst-lead` сверяет контракт данных с обеих сторон (ИИ
  вызывает обоих аналитиков, при необходимости `integration-contract-analyst`).
- **После разработки** — `integration-fix-reviewer` проверяет, не костыль ли фикс (одна сторона
  компенсирует то, что должна решать другая); костыль — возвращай задачу `*-developer-lead`.

`*-analyst-lead` по-прежнему не вызывают друг друга напрямую — обмен только через `integration-lead`.

### Последовательность работы РАЗРАБОТЧИКОВ при кросс-репо задаче (обязательное правило)

Если задача требует изменений на обеих сторонах — **разработчики второй стороны НЕ НАЧИНАЮТ, пока
пользователь явно не утвердил изменения первой** (симметрично в обе стороны). Ограничение только на
этапе реализации — аналитики/библиотекари взаимодействуют свободно на этапе анализа.

Практически: базовая сессия/`integration-lead` запускает `*-developer-lead` сначала для одной стороны,
показывает изменения пользователю и ждёт одобрения, потом запускает вторую. Если
`*-developer-lead` вызван напрямую и не знает, одобрена ли первая сторона — спрашивает у Пользователя.

## Гарантированный признак самостоятельного раздела (когда НЕ спрашивать "разовая область или нет") {#area-sign}

Обычно перед созданием постоянного агента лид спрашивает пользователя. Но если у области есть
структурный признак — спрашивать не нужно, создавай сразу:
- **Сервер**: уже существует свой `*UserComponent`.
- **Клиент**: своя подпапка в `src/views/...` (не один файл) И свой domain `*.d.ts` (как
  `collection.d.ts`).

Исключение — совсем новая фича без такой структуры: тогда её создание (и агента) подтверди с
пользователем как обычно.

## Прямая связь между парой аналитик↔разработчик одной области {#direct-link}

Когда для области существуют ОБА агента, ИИ-разработчик работает в основном автономно и обращается к своему
аналитику НАПРЯМУЮ (не через лидов), заметно реже, чем к библиотекарю:

- Сначала — `*-librarian-lead` за паттернами, как обычно.
- К аналитику — ТОЛЬКО если документации недостаточно для конкретного вопроса: короткий запрос по
  существу ("актуализируй раздел X"), без пересказа контекста задачи.
- Аналитик актуализирует ТОЛЬКО нужный(е) раздел(ы) (`Edit`, не весь файл), проводит через обычную
  проверку у `*-librarian-lead`.
- Аналитик отвечает КОРОТКО — какие разделы/якоря обновлены, не пересказывая содержание; разработчик
  открывает только их.
- Агенту-разработчику такой области нужен `Agent` tool (даётся при создании).

## Состав команд (клиент) {#teams}

- **Библиотекари** (фиксированный состав): `client-librarian-lead` + `client-librarian-docs`
  (документация) + `client-librarian-patterns-general` (общие паттерны) +
  `client-librarian-patterns-gamedev` (геймдев-паттерны клиента; серверный аналог —
  `server-librarian-patterns-gamedev`) + `web-librarian` (внешние источники, общий с server, одинаковые
  копии; хранилище — своё у каждой стороны, [#pattern-gap](#pattern-gap)).
- **Аналитики** — `client-analyst-lead` + агенты по областям, создаются динамически.
- **Разработчики** — `client-developer-lead` + агенты по областям, динамически. MongoDB-персистентность
  — не клиентская область (`server-developer-db-persistence`).
- **Интеграция** (общая с server) — `integration-lead` + `integration-contract-analyst` (сверка
  контракта по коду) + `integration-fix-reviewer` (проверка фиксов на костыли).

Полный состав серверных команд — `/workspace/server/.claude/docs/agent-system-workflow.md`.

## Паттерн не найден — расширение документации {#pattern-gap}

Когда нужного паттерна нет в документации, её расширяют аналитики. Код при поиске паттерна
библиотекари не читают, во внешние источники ходит только `web-librarian`.

1. **Библиотекари.** `*-librarian-patterns-*` ищут только в документации: память, `.claude/docs/`,
   сохранённые web-рекомендации (`.claude/docs/web-recommendations/README.md#search`). Не нашли —
   `НЕ НАЙДЕНО: <паттерн>`; `*-librarian-lead` сразу и синхронно ставит задачу `*-analyst-lead` своей
   стороны и возвращает вызывающему уже ссылку на расширенный раздел.
2. **Области.** `*-analyst-lead` определяет, какие области затрагивает паттерн. Для области есть
   аналитик — задача ему. Область новая — `AskUserQuestion`: поручить наиболее подходящему из
   существующих специалистов (назвать кандидатов) или создать новых специалистов для найденных
   областей.
3. **Исходные данные.** Перед работой аналитик (это правило — для любой задачи аналитика, не только
   паттерна) запрашивает через `*-librarian-lead` документацию проекта, ГДД области и сохранённые
   web-рекомендации. Их недостаточно — задача `web-librarian` (поля `ЗАДАЧА`/`ОБЛАСТЬ` с указанием
   `client`/`server`/`ВХОД`/`ВЕРНУТЬ`: конкретная задача или решение, под которое нужна рекомендация).
4. **Вопросы пользователю.** Вариант, взятый из web-рекомендации, в `AskUserQuestion` помечается
   `[web-рекомендация]` в начале `label` или `description`. После решения пользователя аналитик меняет
   строку `Статус:` рекомендации (`принято`/`отклонено`).
5. **Результат.** Аналитик дописывает раздел паттерна в документацию и регистрирует его через
   `*-librarian-lead` (`#doc-standard`, сокращённый формат).
6. **Разработчики.** Уточнения по паттерну, найденные в работе, разработчик дописывает в саммари
   аналитику отдельным полем `ПАТТЕРНЫ: <паттерн — уточнение>`, док правит аналитик.

Готово, когда у вызывающего есть ссылка на раздел документации с паттерном, а web-рекомендации,
которые пошли в дело, имеют статус.

## Скилл humanizer: только текст для человека {#humanizer}

Скилл `humanizer` (`.claude/skills/humanizer/SKILL.md`, источник — github.com/blader/humanizer,
MIT) убирает из прозы признаки AI-текста. Есть у агентов, чей текст доходит до человека без
пересказа: разработчики (`*-developer-*`) и аналитики (`*-analyst-*`); в `tools` — `Skill`.

- **Когда вызывать** (`Skill`, `skill: "humanizer"`, режим embedded — вернуть только итоговый
  текст): только текст, который человек прочтёт напрямую, —
  - сообщения коммитов и описания PR;
  - итоговый текст разделов `.claude/docs/*.md` (в основном пишут аналитики);
  - вопросы пользователю в `AskUserQuestion` длиннее ~5 строк.
- **Не вызывать** для передачи между агентами (саммари, ответ вызывающему, постановка задачи) —
  она идёт по шаблону [#handoff](#handoff), не прозой; для кода, комментариев, идентификаторов,
  путей, команд, YAML/JSON, код-блоков; для текстов короче нескольких строк.
- **Один вызов в конце задачи**: весь текст для человека (коммит + PR + правка дока) собрать и
  прогнать одним вызовом, не по частям.
- **Писать сразу чисто** (чтобы прогон был нужен реже) — в любом тексте для человека не
  использовать:
  1. «не X, а Y» / «не просто X, а Y», если X никто не утверждал — сказать Y прямо;
  2. фразу-концовку, повторяющую абзац («Это и есть главное.»);
  3. разгон перед мыслью («Давайте разберёмся», «Вот в чём дело», «Честно?»);
  4. спор с несуществующим оппонентом («Это не значит, что…», «Можно было бы…, но»);
  5. остатки чата («Надеюсь, это поможет», «Отличный вопрос», «Хотите, я…»);
  6. жирные ярлыки у каждого пункта списка и натянутые тройки.
- **Поправки для русского текста** (важнее правил скилла):
  - тире, которого требует грамматика (между подлежащим и сказуемым, при пропуске члена
    предложения, перед обобщением), остаётся; правило §8 касается только тире-«связок вместо
    выбора», стиль существующих доков проекта с тире сохраняется;
  - язык не меняется — только русский (см. [#common-rules](#common-rules));
  - имена классов, методов, файлов, якорей и решения пользователя переносятся без изменений.

## Общие правила для всех агентов {#common-rules}

Действуют для КАЖДОГО агента системы; в файлах агентов — короткая отсылка сюда, полный текст здесь.

- **Выбор между вариантами — всегда пользователю** (агенты — полем `ВОПРОСЫ`, [#ask-relay](#ask-relay)); ИИ не выбирает сам даже
  рекомендуемый вариант.
- **Финальный ответ пользователю — только на русском** (касается и субагентов).
- **Кто именно действует — называть явно** ([#who-acts](#who-acts)): «Пользователь» либо «ИИ», а не
  «сам»/«он»/«его», когда речь о личности.
- **Бизнес-логика — по ГДД области** (см. [#gdd](#gdd)): аналитики сверяют с ним ТЗ и код,
  разработчики — свои изменения; расхождение с ГДД не "чинить" молча ни в коде, ни в ГДД — сообщить
  пользователю.
- Плюс правила ниже: точечная передача, resume vs новый вызов, самопроверка кода на риски, экономия токенов, агент не вернул результат,
  проверка на противоречие, кто именно действует, одно правило ГДД — одна функция, переходы состояния без неявного порядка,
  идемпотентность операций, исправление первопричины, сначала убрать — потом добавить,
  порядок вопросов пользователю, вопросы через базовую сессию, внешний источник недоступен, локальный стенд.

### Кто именно действует — называть явно {#who-acts}

В любом тексте, который прочтёт человек (ответ агента, вопрос через `AskUserQuestion`, раздел
`.claude/docs/*.md`, коммит, PR), и в передачах между агентами ([#handoff](#handoff)) личность
называется прямо:

- **Пользователь** — живой человек за клавиатурой, принимающий решения.
- **ИИ** — ассистент: базовая сессия, любой агент системы, любой субагент.

Имена ролей (`client-analyst-lead`, `integration-fix-reviewer` и т.п.) — это ИИ, не отдельная
личность: в тексте для человека они уточняют, какой именно ИИ действует.

Неопределённые местоимения, из которых нельзя понять, о ком речь, не применяются:

- «сам», «сама», «само», «сами» без подлежащего («спроси сам», «не выбирай сам») — заменяются на
  «Пользователь» или «ИИ» («спроси у Пользователя», «ИИ не выбирает»);
- «он», «она», «его», «её», «ему», «им» для человека или ИИ — заменяются на «Пользователь» или
  «ИИ»; если в предложении две личности, местоимение не уточняет, кто именно, — их называют по
  именам роли;
- «кто-то», «кем-то», «некто» — называют личность, если действие совершает человек или ИИ.

Смысл не меняется: «не решай сам» и «решение принимает Пользователь» — одно и то же правило, но во
втором видно, кто решение принимает. Исключения: фразы, где «сам» не про личность, а про свойство
объекта или кода («метод сам проверяет предусловия», «сеттер сам увеличивает `styleID`», «область
сама не меняется»), и речь про третью сущность, а не про Пользователя и ИИ, — их не переписывать.

Любая работа ИИ, не требующая обращения к Пользователю или к другому ИИ, называется автономной —
это и есть случай для «ИИ»: «ИИ-разработчик работает автономно», «ИИ выполняет работу».

Шаг сделан, когда в тексте для человека каждая личность названа «Пользователь» или «ИИ», а
оставшиеся «сам»/местоимения относятся к объекту, коду или третьей сущности.

### Точечная передача задач и информации между агентами {#handoff}

Правило распространяется на ЛЮБОЕ обращение одного агента к другому через Agent tool — не только на
пару аналитик↔разработчик выше — и действует в обе стороны:

- **Постановка задачи** (кто вызывает) — передавай только то, что нужно для этого конкретного шага:
  область, конкретный вопрос/файл/раздел. Не пересказывай весь контекст исходной задачи целиком.
- **Ответ** (кто вызван) — короткий итог по существу: что сделано/выяснено, где посмотреть (файлы,
  разделы, якоря). Не пошаговый пересказ хода работы; детали остаются в файлах.
- **Исключение** — получатель делает ОДНОЗНАЧНЫЙ запрос на более широкий контекст (явно
  формулирует, что именно и зачем ИИ его не хватает) — тогда передать запрошенное, но только после
  согласования с пользователем.
- **Формат передачи** — поля, не связный текст (короче для получателя, и humanizer не нужен):

  ```
  СДЕЛАНО: <пункты, по одному факту>
  ФАЙЛЫ: <путь:строки — что изменено/где смотреть>
  РЕШЕНИЯ: <решение — кто принял (пользователь/агент), причина>
  ПРИЧИНА: <файл:строка — почему; только у фикса бага, #root-cause-fix>
  ОТКРЫТО: <риски, что не сделано; "нет", если пусто>
  РИСКИ: <только разработчик: метод — риск — исправлено/вопрос, см. #code-risk-check>
  ВОПРОСЫ: <вопросы пользователю по #ask-relay; поле опускается, если вопросов нет>
  ```

  Постановка задачи — `ЗАДАЧА` / `ОБЛАСТЬ` / `ВХОД` (файлы, разделы, якоря) / `ВЕРНУТЬ`. Поля без
  содержания опускаются. Связный текст пишет только тот, кто отдаёт его человеку
  (см. [#humanizer](#humanizer)); саммари разработчика аналитику по итогам — тоже по шаблону, с
  полнотой, достаточной для `#doc-standard`.

### Переиспользование агента (resume) vs. новый вызов

В Claude Code НЕТ команды сжатия/сброса контекста существующего экземпляра субагента "на месте" — ни
для вызывающего, ни для самого агента; `/compact` работает только в основной сессии. Единственный
способ получить чистый контекст — новый вызов через `Agent` tool:

- По умолчанию каждое обращение к другому агенту — НОВЫЙ вызов через `Agent` tool, не resume
  существующего экземпляра по его agentId.
- Resume (через SendMessage) — только чтобы продолжить ОДНУ и ту же тему в рамках текущего обмена
  (например, уточняющий вопрос сразу после ответа того же агента).
- Пришла новая, не связанная с прошлым обращением тема — НЕ resume, новый вызов с нуля, даже если
  агент того же типа уже использовался ранее в сессии.
- Resume того же экземпляра оказался "холодным" (кэш не сработал, например после большого перерыва) и
  накопленный контекст уже большой — не продолжай resume разрастающегося треда: сформулируй короткое
  саммари уже установленных фактов/решений и передай его как prompt НОВОМУ вызову через `Agent` tool.

### Самопроверка кода на риски {#code-risk-check}

Разработчик (`*-developer-*`), написав или изменив метод, до передачи результата проверяет каждый такой
метод по списку и чинит найденное в объёме задачи; вне объёма или с выбором — в `ВОПРОСЫ`:
- данные из БД/запроса битые, пустые или устаревшие (отсутствует поле, неизвестный enum, 0/отрицательное);
- исключение посреди метода: что уже списано, удалено, записано в БД — состояние остаётся целым;
- повтор, гонка, отложенный тик после отмены;
- проверка держится на вызове в другом месте ([#no-implicit-order](#no-implicit-order));
- молча пропущенное значение (тип, ветка, `null`) вместо ошибки.

Результат — поле `РИСКИ: <метод — риск — исправлено/вопрос>` в отчёте; `нет`, если не найдено. Шаг
сделан, когда в поле есть каждый написанный или изменённый метод с бизнес-смыслом.

### Экономия токенов {#token-economy}

Правила по итогам почасовой проверки (`CLAUDE.md`, «Контроль расхода токенов»), одна строка на правило:

- **Точечное чтение документов.** Правка или проверка раздела `.claude/docs/*.md` — `grep -n` по якорю,
  затем `Read` с `offset`/`limit` только этого раздела; документ целиком читается только при создании
  или полной перепроверке. Вызывающий пишет в `ВХОД` якоря, а не только путь. Регистрация правки у
  `*-librarian-lead` — проверка только изменённых разделов.
- **Длинный тред — новым вызовом.** Уточнение по области после того, как тред лида разросся (≳100K) —
  новый вызов аналитика области с короткой сводкой решений вместо resume лида.
- **Длинная базовая сессия — /compact между этапами.** Флаг ratio у TOTAL при длинном контексте
  базовой сессии — по завершении этапа (одобрение стороны, конец волны) предложить пользователю
  `/compact`, предварительно записав решения в ГДД/контракт/память.

### Агент не вернул ожидаемый результат {#no-result}

Если вызванный агент вернулся без ожидаемого результата (нет вердикта/ответа, "запустил фоновую
проверку — дождитесь уведомления" и т.п.) — ИИ не выполняет работу вместо него и не запускает новый экземпляр сразу:

1. Переспроси ТОГО ЖЕ агента (`SendMessage` по его ID — это продолжение той же темы, см. resume выше):
   он ещё в процессе, результат уже выдан, но не был замечен, или произошёл сбой?
2. Агент в процессе — дождись его результата/уведомления. Результат был выдан — возьми его. Сбой —
   пусть ИИ доведёт работу до результата.
3. Только если агент не отвечает или отвечает некорректно — ИИ выполняет работу сам (или новый вызов
   агента того же типа) и сообщает пользователю, что прежний вызов не дал результата.

### Проверка на противоречие с ранее принятыми решениями

Прежде чем зафиксировать ответ пользователя как окончательное решение (в документации, коде,
архитектуре) — проверь по документации/памяти этой же области, нет ли более раннего решения, которому
новое явно противоречит. Если есть — не принимай молча, переспроси: "Вы уверены? Ранее здесь было
решено X (причина: Y), новое решение этому противоречит — возможные последствия: Z." Продолжай только
после явного повторного подтверждения. Это дополнительная проверка поверх обычного
`AskUserQuestion`, а не замена ему — применяется, когда есть основания подозревать конфликт с прошлым
решением в той же зоне.

### Одно правило ГДД — одна функция {#gdd-function-mapping}

Каждая функция с бизнес-смыслом (проверка состояния, условие, действие) сопоставляется с конкретным
правилом ГДД, которое она реализует. Одно правило/условие ГДД — одна функция; дубли по смыслу
недопустимы, даже если у них разные имена.

- **Аналитики** (при анализе кода и при проектировании решения): для каждой затронутой и каждой
  предлагаемой функции назови правило ГДД (`#gdd-<раздел>`), которое она выражает. Найди функции,
  выражающие ТО ЖЕ правило: разные имена с одним смыслом, одна — тонкая обёртка другой (`return other()`),
  константа в одном наследнике и та же проверка в другом. Такие пары — обязательная находка анализа
  с предложением оставить одну функцию (имя — по смыслу ГДД, а не по месту вызова). Предлагаемое
  решение не должно вводить новую функцию, если правило уже выражено существующей.
- **Разработчики**: перед добавлением функции с бизнес-смыслом — `grep` по классу и иерархии на
  функции того же смысла; нашлась — использовать её, а не добавлять ещё одну (имя не подходит — см. ниже). Найденный
  дубль вне объёма задачи — сообщить, не чинить молча.
- **Имя существующей функции не соответствует новому смыслу.** Если правило уже выражено функцией,
  но её имя не ассоциируется с разрабатываемой логикой — не переименовывать молча и не заводить
  дубль-обёртку, а спросить пользователя (`AskUserQuestion`) о переименовании, предварительно
  сообщив: где и при каких условиях функция вызывалась до сих пор (файл:строка, сценарий) и где/при
  каких условиях будет вызываться в новом решении; варианты — переименовать (предложить имя по смыслу
  ГДД) / оставить имя.
- **Документация** (п.7 [стандарта](#doc-standard)): у метода с бизнес-смыслом — какое правило ГДД он
  реализует; два метода с одной ссылкой на правило — сигнал дубля.

Прецедент (коллекции, 2026-10-05): `isDropEnabled()` (альбомы — `= isSectionActive()`, танки — `true`)
и `isSectionActive()` выражали одно правило «секция активна, пока идёт событие» (`#gdd-ops-season`),
анализ этого не выявил; `isDropEnabled` убран.

### Переходы состояния — у владельца, без неявного порядка вызовов {#no-implicit-order}

Корректность не должна зависеть от того, что вызывающий код выполняет шаги над состоянием ДРУГОГО
объекта в определённом порядке («сначала снять флаг, потом вызвать сеттер», «сначала A, иначе B
сломается»). Такой порядок нигде не выражен в типах/API и ломается при следующей правке вызывающего.

- **Переход состояния — один метод у владельца.** Флаги жизненного цикла, condition-биты, сезон и
  т.п. меняет только объект, которому они принадлежат: один публичный метод на переход, имя по смыслу
  перехода; метод сам выполняет все шаги и сам проверяет предусловия. Публичный метод, корректный
  лишь при условии, что до него вызвали другой метод, — сигнал свернуть пару в один.
- **Аналитики** (анализ и проектирование): места, где вызывающий выполняет последовательность шагов
  над чужим состоянием (снять/поставить флаг + сеттер, сброс + пересчёт в разных местах), —
  обязательная находка с предложением метода-перехода у владельца. Предлагаемое решение не
  проектирует API, требующий определённого порядка вызовов.
- **Разработчики**: не писать код, где вызывающий выполняет шаги перехода состояния другого объекта;
  нужного перехода нет — добавить метод у владельца (с учётом [#gdd-function-mapping](#gdd-function-mapping)).
  Найденное вне объёма задачи — сообщить, не чинить молча.
- **Документация**: у метода-перехода — из какого состояния в какое он переводит объект.

Прецедент (коллекции, 2026-10-05): `Collection.addItem` снимал `INTERNAL_CONDITION_DELETED` с
`CollectionItemEntry`, а затем вызывал `entry.setStars(...)` — `setStars` был корректен лишь при
условии, что флаг снят раньше. Заменено одним методом-переходом `CollectionItemEntry.updateState(Stars)`.

### Идемпотентность операций {#idempotent-ops}

Операция, которая выдаёт награду, списывает ресурс или переводит состояние, при повторе (двойной
клик, повторный запрос, повторное уведомление о платеже) и после обрыва посередине оставляет то же
состояние, что после одного выполнения.

- **Защита от повтора — у владельца состояния, на сервере**: проверка «уже выдано/уже принято» и
  смена состояния — в одном методе-переходе ([#no-implicit-order](#no-implicit-order)). Блокировка
  кнопки на клиенте — UX, защитой от повтора она не считается.
- **Клиент**: повторный ответ или push не меняет модель второй раз — применять пришедшее значение, а
  не прибавлять дельту к уже применённой.
- **Аналитики** (анализ и проектирование): для каждого затронутого и предлагаемого роута с выдачей,
  списанием или переходом состояния — ответ на два вопроса: что даёт повторный вызов; что остаётся
  при падении между шагами (выдано без отметки, списано без выдачи). Неидемпотентный роут —
  обязательная находка.
- **Разработчики**: новый или изменённый такой роут — с проверкой повтора у владельца; в саммари
  (`СДЕЛАНО`) — что даёт повторный вызов. Атомарность требует менять запись в БД — серверная сторона
  через `server-developer-db-persistence` (подход выбирает пользователь). Найденное вне объёма
  задачи — сообщить, не чинить молча.

Прецеденты (отложенное): двойная выдача набора при повторном уведомлении о платеже (магазин);
повторная награда в `completeQuest` (квесты); новый бустер на каждый повторный `/summonAccept`
(военная база).

### Таймеры — без серверного планировщика {#no-server-scheduler}

Событие, которое по ГДД наступает по истечении времени (сундук готов, производство закончилось,
лимит восстановился), запускает запрос клиента, а не планировщик на сервере (`scheduler().scheduleOnce`,
`ScheduledExecutorService`, периодический тик актора).

- **Сервер хранит абсолютное время окончания** (ленивый таймер, как `airDropDeadTime` в AirDrop) и
  вычисляет состояние при обращении.
- **Таймер ведёт клиент**: отсчёт от оставшегося времени из ответа сервера, а не от своих часов против
  серверного дедлайна. По истечении клиент шлёт уточняющий запрос (открыть, забрать, обновить
  состояние или значок).
- **Сервер проверяет запрос**: время по серверным часам действительно истекло — выполняет и отвечает
  по смыслу запроса; не истекло — ответ с актуальным состоянием и временем окончания, клиент
  перезапускает таймер. Проверка и переход — в одном методе у владельца
  ([#no-implicit-order](#no-implicit-order)), повторный запрос безопасен ([#idempotent-ops](#idempotent-ops)).
- Событие нужно, когда клиента нет (рассылка другим игрокам, глобальный сброс), — вопрос
  пользователю через `ВОПРОСЫ`, а не планировщик.
- **Аналитики** (анализ и проектирование): каждое правило ГДД «по истечении времени» проектируется
  как «клиентский таймер → запрос → проверка на сервере». Серверный планировщик в области —
  обязательная находка.
- **Разработчики**: серверный планировщик не добавлять; найденный вне объёма задачи — сообщить, не
  чинить молча.

Прецедент (лутбоксы, 2026-10-28): значок «ТРОФЕИ» был на `scheduleOnce` актора, переделан на
`/ingame/lootbox/checkReady` → `{remaining}`.

### Исправление первопричины {#root-cause-fix}

Шаги для любого бага. На стыке client/server дополнительно — `integration-fix-reviewer`
([#integration](#integration)).

1. **Воспроизвести.** Назвать сценарий и `файл:строка`, где значение или состояние становится
   неверным, — отдельно от строки, где падает или видно симптом. Наблюдаемое поведение — локальный
   стенд по одобрению ([#local-stand](#local-stand)); без него — вывод по коду с пометкой «не
   воспроизведено». Критерий: названо место возникновения, а не только место падения.
2. **Чинить там, где возникает.** Проверка на `null`/`undefined`, `?? default`, `try/catch` или
   ранний `return` в месте падения, когда неверное значение рождается выше по пути данных, —
   **костыль**: прячет падение, баг всплывёт у следующего потребителя.
3. **В саммари** — `ПРИЧИНА: <файл:строка — почему>`. Фикс оказался в месте симптома — там же
   объяснить, почему причину не исправить, и вынести вопрос пользователю через `ВОПРОСЫ`.

Аналитики при разборе бага указывают место возникновения и место падения раздельно.

### Сначала убрать, потом добавить {#subtract-redesign}

Новое требование встраивается так, как будто оно было в области с самого начала, а не
прикручивается сбоку к старому дизайну. **Прикручивание** — новый флаг или ветка `if` по типу в
нескольких местах, параметр ради одного вызывающего, копия класса с одним отличием.

- **Аналитики** (проектирование): кроме решения «добавить к текущему» — как выглядела бы область,
  будь требование в ней с начала. Варианты различаются — оба пользователю через `ВОПРОСЫ`, с
  объёмом и поставкой по частям, каждая часть проверяема отдельно.
- **Разработчики**: перед добавлением — удалить то, что новое требование делает ненужным (ветки,
  параметры, мёртвый код на пути изменения). Прочее удаление и рефакторинг вне объёма задачи —
  сообщить как кандидата, не делать молча. Согласованное решение по ходу работы требует
  прикручивания — остановиться и вернуть вопрос аналитику или пользователю.

### Контракт client↔server — дополнять, а не плодить типы {#contract-reuse}

Контракт обмена данными client↔server (JSON ответа/push, DTO, `*.d.ts`) по возможности описывает
основную информацию механики одним набором типов. Новое требование сначала ложится в имеющиеся типы,
и только если они для него не подходят, заводится новый тип.

- **Сначала дополнить имеющееся.** Новые данные — это необязательное поле (`field?: T` на клиенте,
  поле, которое может отсутствовать в JSON, на сервере) в типе, который уже передаёт ту же сущность.
  Если ответы разных роутов отличаются набором полей вокруг одной сущности — общая часть выносится в
  базовый тип, а ответы от него наследуются (`extends`): `LootboxOpenResultJSON extends LootboxResponseJSON`.
- **Признак лишнего типа** — новый интерфейс или DTO, который повторяет поля имеющегося, отличается
  от него одним-двумя полями или передаёт ту же сущность под другим именем.
- **Лёгкий роут для мелкого события** (проверка готовности, отметка «просмотрено», значок) может
  получить свой маленький интерфейс ответа, как `LootboxCheckReadyJSON { remaining? }` для
  `/ingame/lootbox/checkReady`. Сначала аналитик сравнивает альтернативы: хватит ли ответа без тела
  (просто «успешно»), push-события, поля в уже приходящем ответе или push. Отдельный интерфейс
  заводится, если ни одна альтернатива не подходит, и в архитектуре одной строкой объясняется почему.
- **Аналитики** (проектирование): для каждого предлагаемого типа контракта указать, какой имеющийся
  тип он дополняет или от какого наследуется. Новый самостоятельный тип допустим, если это новая
  сущность, и тогда в архитектуре одной строкой объясняется, почему имеющиеся типы не подходят. Лишние
  типы в затронутом контракте — обязательная находка с предложением, как их объединить.
- **`integration-lead`** при согласовании контракта проверяет это правило с обеих сторон: одна
  сущность — один базовый тип у клиента и у сервера.
- **Разработчики**: тип контракта, которого нет в согласованной архитектуре, не заводят. Если без него
  не обойтись — вопрос аналитику. Объединение имеющихся типов за пределами задачи — сообщить как
  кандидата, молча не делать.

### Имена — полные слова, не длиннее 3 слов {#naming-rules}

Имена новых функций, методов, переменных, полей и параметров — без сокращений слов, не больше 3
слов, из простых английских слов, привычных русскоязычным программистам. Правила и исключения —
скилл `naming`, раздел «Полные слова и длина имени».

- **Аналитики** (проектирование): имена, которые архитектура вводит (функции, поля, типы контракта),
  подбираются через скилл `naming` до передачи разработчикам.
- **Разработчики**: перед тем как назвать новую сущность в коде — скилл `naming`. Сокращения в
  старом коде вне задачи не переименовываются ([#subtract-redesign](#subtract-redesign) — сообщить
  кандидатом).

### Порядок вопросов пользователю {#question-order}

В один вызов `AskUserQuestion` попадают только **независимые** вопросы: ни один вариант ответа на
любой из них не влияет на то, нужен ли другой вопрос этого вызова и какие у него варианты.

- **Зависимый вопрос** — у предыдущего вопроса есть вариант, который делает этот вопрос ненужным
  или меняет его варианты (например, «делать миграцию?» с вариантом «нет» → «каким способом
  мигрировать?»). Его задают отдельным, следующим вызовом `AskUserQuestion` — после того как ответ на
  предыдущий получен и разобран; по ответу «нет» он не задаётся вовсе.
- **Проверка перед вызовом**: пройти по каждому варианту каждого вопроса и спросить себя, снимает
  или меняет ли он какой-то другой вопрос вызова. Да — зависимый вопрос убрать из вызова и задать
  позже. Шаг сделан, когда в вызове не осталось ни одного такого варианта.
- **Вопросы для пересылки**: агент возвращает вопросы полем `ВОПРОСЫ` ([#ask-relay](#ask-relay)),
  зависимые помечает «задать после ответа на п.N»; базовая сессия задаёт их по этой пометке.
- Правило действует и для базовой сессии.

### Вопросы пользователю от агентов — через базовую сессию {#ask-relay}

`AskUserQuestion` у субагентов недоступен: Claude Code убирает его из инструментов любого субагента
независимо от `tools` (code.claude.com/docs/en/sub-agents, «Available tools»; проверено 2026-10-13).
Пользователя спрашивает только базовая сессия. Везде, где регламенту или файлу агента нужно решение
пользователя («спроси пользователя», «на выбор пользователю», поле `ВОПРОСЫ`), агент действует так:

1. **Развилка — пауза.** Работу, которая от ответа не зависит, агент доделывает; на развилке
   останавливается и возвращает поле `ВОПРОСЫ` ([#handoff](#handoff)). По каждому вопросу: текст,
   2–4 варианта с последствиями, рекомендуемый — первым с пометкой «(Рекомендуется)», пометка
   `[web-рекомендация]` где применимо, зависимые — «задать после ответа на п.N»
   ([#question-order](#question-order)). Сам вариант не выбирает и не продолжает по «наиболее
   вероятному».
2. **Вложенный агент** отдаёт `ВОПРОСЫ` своему вызывающему; тот переносит их в свои `ВОПРОСЫ` без
   пересказа — и так до базовой сессии. Ответы спускаются обратно тем же путём через `SendMessage`.
3. **Базовая сессия** задаёт вопросы через `AskUserQuestion` и передаёт ответы тому же экземпляру
   агента через `SendMessage` (продолжение темы, см. resume) полем `РЕШЕНИЯ ПОЛЬЗОВАТЕЛЯ`; агент
   продолжает с места паузы.
4. **Предсказуемые вопросы** (ГДД по [#gdd](#gdd), создание агента без гарантированного признака
   раздела, выбор области) базовая сессия задаёт до запуска и передаёт ответы в постановке задачи.

Шаг сделан, когда в результате агента нет ни одного решения, принятого без ответа пользователя.

### Внешний источник недоступен {#source-unavailable}

Касается каждого, кто читает внешние источники: ссылки из постановки задачи, документацию SDK и
библиотек, результаты `WebSearch`/`WebFetch`. Действует и для базовой сессии.

1. **Ошибка чтения — альтернативы.** Ссылка не открылась или чтение прервалось (HTTP-код, таймаут,
   редирект на логин, пустой или обрезанный ответ, бинарный файл вместо текста) — пробуй получить те
   же данные другим путём: markdown/raw-версия страницы (`.md`, raw-файл на GitHub), соседняя
   страница той же официальной документации, `WebSearch` по точному названию метода или раздела.
   Готово, когда данные получены или каждый альтернативный путь тоже завершился ошибкой.
2. **Все пути не сработали — пауза на этих данных.** Недостающее не восполняй памятью модели или
   догадкой и не продолжай работу, которая от него зависит. Независимую часть доделай
   ([#ask-relay](#ask-relay), п.1) и верни поля:

   ```
   ИСТОЧНИК НЕДОСТУПЕН: <URL> — <шаг задачи, где он нужен> — <ошибка дословно> — <какие альтернативы пробовал и чем они кончились> (по строке на ссылку)
   НЕ ХВАТАЕТ: <каких данных нет (метод, параметры, коды ошибок, ограничения площадки) и какое решение от них зависит>
   ВОПРОСЫ: как действовать дальше — варианты: пользователь пришлёт текст/файл страницы; другая ссылка; продолжить без этих данных с пометкой «не подтверждено источником»; остановить задачу
   ```

   Базовая сессия задаёт тот же вопрос через `AskUserQuestion`, перед этим назвав место ошибки и
   недостающие данные.

Шаг сделан, когда каждая недоступная ссылка названа с местом и текстом ошибки, а ни один факт из неё
не выдан за прочитанный.

### Локальный стенд для отладки {#local-stand}

**Стенд** — игра на `http://localhost:8080/`: клиент против локального сервера (`/workspace/server`,
`server.port` = 8080) и локальной MongoDB. Данные тестовые. Стенд запускает и держит пользователь:
ветка, сборка и данные в БД на нём могут не совпадать с кодом, который ты читаешь.

Когда звать: код и документация не дают ответа, а нужно наблюдаемое поведение — воспроизвести баг,
проверить фикс, увидеть фактический ответ сервера или состояние игрока. Действует для всех агентов
и базовой сессии.

1. **Запрос через пользователя.** Агент обращается к стенду только после явного «да» на конкретный
   запрос. Агент возвращает ([#ask-relay](#ask-relay)):

   ```
   ЗАПРОС СТЕНДА: <что проверить> — <какое решение от этого зависит> — <только чтение | изменение данных: какие действия/dev-роуты>
   ВОПРОСЫ: стенд запущен и можно проверить? нужна ли подготовка (аккаунт, данные, ветка, пересборка)?
   ```

   Базовая сессия задаёт вопрос через `AskUserQuestion` и передаёт ответ тому же экземпляру агента.
   Готово, когда есть «да» пользователя на этот запрос; «нет» — работа продолжается без стенда.
2. **Доступ.**
   - HTTP — ИИ через `Bash`/`curl`: живость стенда
     (`curl -s -m 5 -o /dev/null -w "%{http_code}" http://localhost:8080/` → `200`), статика
     `assets/static/*`, HTTP-роуты сервера.
   - Игровой UI (PIXI-canvas) и WS-роуты `/ingame/*` через `curl` не проверить. Их проверяет базовая
     сессия браузерными инструментами, если они подключены (Claude in Chrome, встроенный браузер);
     иначе агент отдаёт сценарий шагами, пользователь выполняет его и присылает результат
     (скриншот, лог консоли, ответ сервера).
   - Стенд не отвечает — ошибку дословно в `ВОПРОСЫ` (пользователь поднимет стенд / продолжить
     без него); состояние стенда не додумывать.
3. **Изменение данных** (dev-роуты `/ingame/devTools/*`, покупки, сброс прогресса, правка БД) —
   только действия, перечисленные в одобренном запросе. Новое действие — новый запрос по п.1.
4. **Результат** — поле в ответе:

   ```
   СТЕНД: <что сделано> — <наблюдаемое дословно: код ответа, текст, скриншот/лог> — <на какой ветке/сборке, если пользователь назвал>
   ```

   Наблюдение со стенда подтверждает или опровергает гипотезу. В документацию как факт о поведении
   идёт только подтверждённое кодом ([#doc-standard](#doc-standard), «Актуальность»); расхождение
   стенда и кода — в `ОТКРЫТО`.

Шаг сделан, когда каждое обращение к стенду покрыто одобренным запросом, а каждое наблюдение
записано в `СТЕНД` дословно.

## Стандарт документации компонента {#doc-standard}

Документ о компоненте, который `*-analyst-lead`/`*-developer-lead` передаёт библиотекарям на
регистрацию, ОБЯЗАН содержать (объём — см. "Масштабирование глубины"):

1. Краткое описание: назначение и бизнес-логика.
2. Использованные референсы, если есть.
3. Использованные паттерны, если есть.
4. Полный список созданных/изменённых классов.
5. Ссылки (якоря) для навигации по документу.
6. Оглавление по классам из п.4, с переходами по ссылкам из п.5.
7. Для каждого класса — назначение и описание методов; у метода с бизнес-смыслом — какое правило
   ГДД он реализует (см. [#gdd-function-mapping](#gdd-function-mapping)).
8. Принятые уязвимости/компромиссы и причины, если есть.
9. Связь с ГДД (см. [#gdd](#gdd)): в начале документа — ссылка на ГДД области; у каждого раздела/
   класса, реализующего правило бизнес-логики, — ссылка на конкретный раздел ГДД
   (`…/game-design/<область>-gdd.md#gdd-<раздел>`). ГДД ещё нет — вместо ссылки строка
   `ГДД: отсутствует`, и отправитель обязан запустить его создание по [#gdd](#gdd).
10. Карта файлов компонента — отдельный раздел с полным списком файлов, участвующих в работе
    компонента (путь от корня репозитория + одна строка роли), в двух подразделах:
    - **Файлы прямого влияния** — непосредственно реализуют компонент: сам компонент, его модели,
      DAO, справочники данных, страница/роуты, типы, вью. Пример (коллекции, server):
      `CollectionUserComponent`, `CollectionDao`, `CollectionData`.
    - **Файлы косвенного влияния** — файлы других областей, где компонент подключается или
      учитывается дополнительно: регистрация/инициализация, правила ГДД, исполняемые в чужом коде,
      интеграционные точки (контракт client↔server, push-события, dev-инструменты). Пример:
      `User`, `Balance`, `DevToolsPage`.
    Пограничные случаи (решение пользователя 2026-10-13):
    - миграции и атласы самого компонента — прямое; общие ресурсы, где компоненту принадлежит
      часть (`balance.json`, `ru.json`), — косвенное, в роли — какая таблица/ключи;
    - типы и утилиты другой области, которые компонент использует (`ItemType`, enum-ы полей,
      commons) — косвенное, роль начинается со слова «зависимость»;
    - мёртвые вхождения (неиспользуемая константа, упоминание в комментарии) в карту не входят;
      неиспользуемый код компонента — в п.8 как кандидат на удаление.
    Отличие от п.4: п.4 — что создано/изменено в задаче, п.10 — весь компонент целиком.
    Критерий полноты: `grep` по именам классов прямого влияния по всему репозиторию — каждый файл
    с вхождением стоит в одном из подразделов.

Документ читаем для человека, не телеграфным стилем — но и без лишнего (см. ниже).

Реестр документации компонентов (компонент → документ, статус, дата обновления) —
`.claude/docs/component-docs-registry.md`; ведёт только `client-librarian-lead`: агенты, создавшие или
обновившие документ, передают его на регистрацию, а не правят реестр сами.

У агентов-специалистов (все, кроме `*-lead`) — личная память (`memory: local`, папка
`.claude/agent-memory-local/<агент>/`); правила и лимиты — `/workspace/client/.claude/docs/agent-memory.md`.

Документация от аналитиков по существующему коду (не по итогам разработки) всегда помечается
**auto-create** и используется с меньшим доверием — библиотекари обязаны явно сообщать об этой
пометке. Документ по коду, написанному в этой же задаче по ГДД или ТЗ, — `обычный`, даже если его
составил аналитик по коду.

### Покрытие кода сканированием {#scan-coverage}

Отправитель документа на регистрацию (`*-analyst-lead`, `*-developer-lead`) добавляет к передаче
поле `ПРОСКАНИРОВАНО: <пути файлов кода>` — файлы, прочитанные в этой задаче целиком, включая
прочитанные аналитиками областей (лид требует это поле в `ВЕРНУТЬ` их задач). Файлы, найденные только
`grep` или прочитанные фрагментом, в поле не входят. Нет поля — документ не регистрируется, это пункт
в списке несоответствий. По полю `*-librarian-lead` ставит отметки в
`.claude/docs/source-scan-coverage.md` (процедура — в шапке файла).

### Масштабирование глубины (важно для стоимости, не только полноты)

- **Полный формат** (все 10 пунктов, метод-за-методом для нетривиальной логики) — для нового
  компонента/фичи целиком.
- **Сокращённый формат** — для расширения уже задокументированного компонента: п.1 сжато, п.7 только
  для изменённых методов, п.8 если применимо, п.9 — для изменённых мест, п.10 — дополнить новыми файлами и
  перепроверить подраздел у изменённых; п.2-6 можно пропустить со ссылкой на существующий
  документ.
- **Тривиальные геттеры/сеттеры/делегаты** — одной строкой списком, не абзацем. Подробно — только
  методы с реальной логикой.

### Самопроверка перед отправкой

`*-analyst-lead`/`*-developer-lead` сам сверяется со всеми применимыми пунктами и устраняет пробелы
ДО отправки библиотекарю. Проверка библиотекаря — контроль качества, а не первая обратная связь по
структуре: рассчитывай пройти с первого раза.

### Проверка перед регистрацией

`*-librarian-lead` (не конкретный специалист) проверяет документ на соответствие ДО регистрации.
**Исчерпывающе за один проход**: сверяет ВСЕ пункты целиком и при отказе возвращает ПОЛНЫЙ список всех
несоответствий сразу — не по одному на круг (каждый лишний круг — отдельный дорогой вызов).

### Защита от бесконечного цикла

Отправитель сам считает отказы подряд по одному документу. 3 отказа без новых изменений между
попытками — прекратить и эскалировать пользователю через `AskUserQuestion` с описанием проблемы.

### Актуальность: документируй только то, что подтверждено кодом

При обновлении документа сверяй утверждения о методах/полях/путях с реальным кодом (`grep`/`Read`), а
не с прошлой редакцией документа. Устаревшие пункты и компромиссы, которые уже неактуальны, —
удаляй, а не помечай зачёркиванием: историю хранит git. Исключение — короткая заметка "история
контракта", если без неё есть риск снова принять уже опровергнутое предположение.

## Документ игрового дизайна (ГДД) {#gdd}

**Где.** Одна копия на обе стороны: `/workspace/client/.claude/docs/game-design/<область>-gdd.md`.
Сервер своей копии не заводит — архитектурные документы сервера ссылаются на клиентский файл
абсолютным путём. Шаблон и соглашения — `/workspace/client/.claude/docs/game-design/README.md`.
В страховочной раскладке та же копия лежит по тому же пути, с именем каталога в корне репозитория.

**Назначение.** Источник истины по бизнес-логике области — ЧТО и ПОЧЕМУ должно происходить с точки
зрения игры, а не КАК это реализовано (реализация — в архитектурных документах). ГДД:
- хранит правила бизнес-логики;
- дополняется при правках логики;
- проверяется на логические противоречия и недостаточность информации.

**Создание** (делает `*-analyst-lead` при анализе области, либо аналитик области, если ГДД ещё нет):
1. Запроси у пользователя через `AskUserQuestion` файл с описанием логики (путь к файлу).
2. Файла нет — запроси у пользователя примерное описание фичи; ГДД помечается статусом
   `черновик — по примерному описанию`.
3. **До написания ГДД предложи пользователю структуру** (список разделов с якорями `#gdd-<раздел>`
   и одной строкой — что в каждом) и согласуй её через `AskUserQuestion`. Писать документ — только
   после явного согласия. Затем перепиши источник оптимизированно: по согласованным разделам, без
   воды и повторов, но без потери правил; числа, условия и формулировки ограничений — дословно.
4. Не выводи бизнес-логику из кода самостоятельно: код — это реализация, он может содержать баги.
   Правило, найденное в коде, попадает в ГДД только после подтверждения пользователя.
5. Неоднозначности и пробелы — не додумывай: в раздел "Открытые вопросы" + вопрос пользователю.
6. Регистрация — через `*-librarian-lead` (проверка по шаблону README, запись в `MEMORY.md` с
   пометкой `[ГДД]`).

Для уже задокументированных областей без ГДД — ретроактивно не создавать; ГДД запрашивается при
следующей задаче по этой области.

**Дополнение.** Информация может поступать частями, ГДД дополняется по ходу работы с кодом. Когда при
аналитике/разработке всплывает новое правило, правка логики или пробел — **способ дополнения и
содержимое уточняй у пользователя** до внесения (`AskUserQuestion`: новый раздел / изменить
существующий раздел / записать в "Открытые вопросы" / не фиксировать). Правка — точечно `Edit`.

**Журнал изменений — минимальный.** Запись (дата + одна строка "было → стало") делается ТОЛЬКО при
изменении уже описанной логики. Новые разделы и дополнения, не меняющие описанное, вносятся в ГДД
напрямую, без записи в журнал.

**Проверка** — при каждом создании/дополнении ГДД и при каждом новом ТЗ по области, строго по порядку:
1. **Противоречия внутри ГДД** (включая новое ТЗ против ГДД — по [проверке на противоречие](#common-rules):
   переспросить с прежним решением, причиной и последствиями) — согласовать с пользователем и
   устранить в ГДД.
2. **Только после этого — противоречия между ГДД и кодом/архитектурой** обеих сторон: сообщить
   пользователю, что именно расходится. Пока внутри ГДД есть несогласованные противоречия, сверку с
   кодом не начинать.

### Недостаточность {#gdd-insufficiency}

Проверяется на любом шаге: при создании и дополнении ГДД, при новом ТЗ, при анализе области под
задачу. Ответ на пробел не додумывай: запиши его в "Открытые вопросы" и спроси пользователя.
Шаг завершён, когда по каждому затронутому правилу каждый пункт списка либо описан в ГДД, либо стоит
в "Открытых вопросах".

- граничные случаи и лимиты;
- повторы и дубликаты;
- сброс и миграция прогресса;
- поведение при ошибке и что при этом видит игрок;
- **нестандартные действия игрока** — по каждому действию, которое шлёт запрос на сервер, тратит
  ресурс или выдаёт награду:
  - двойное или быстрое повторное нажатие, повторная отправка;
  - закрытие окна или уход с экрана, пока ответ не пришёл;
  - обрыв сети, ошибка или таймаут посреди цепочки запросов; перезаход в игру после этого;
  - игра открыта в двух вкладках или на двух устройствах;
  - вкладка ушла в фон и вернулась: таймеры, отложенные события, пропущенные push;
  - подделка запроса клиентом: что сервер обязан проверить сам.

**Связь с архитектурой** (п.9 [стандарта](#doc-standard)). У каждого раздела ГДД — стабильный якорь
`{#gdd-<раздел>}`. Архитектурные документы обеих сторон ссылаются на эти якоря из соответствующих
разделов/классов, чтобы при формировании или рефакторе архитектуры сразу открыть нужное правило — читай
разделы ГДД по ссылкам, а не весь файл. Переименование/удаление якоря ГДД — `grep` по имени файла ГДД
в `.claude/docs/` обоих репозиториев и обновить ссылки.
