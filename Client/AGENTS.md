# Корень инструкций — папка WF вне контейнера

Все файлы инструкций проекта (этот файл, `AGENTS.md` и раскладка агентов: команды, скиллы, документация,
память) живут в одной папке WF **вне контейнера** и правятся только там: у клиента это `$WF_ROOT/Client`.
Рабочий каталог `/workspace/client` подключён к ней симлинками `CLAUDE.md`, `AGENTS.md` и `.deepseek/`.

1. Проверка: `echo $WF_ROOT; ls -l /workspace/client/CLAUDE.md /workspace/client/AGENTS.md
   /workspace/client/.claude /workspace/client/.deepseek` — все четыре ссылки ведут в `$WF_ROOT/Client`.
   Переменная не задана, ссылки битые или указывают мимо папки WF — остановиться, ничего не создавать и
   не перезаписывать рядом (копия в контейнере теряется при пересоздании и расходится с источником),
   спросить Пользователя.
2. Пути в этом файле записаны относительно папки инструкций клиента `$WF_ROOT/Client`: `.deepseek/docs/...`
   читается как `$WF_ROOT/Client/.deepseek/docs/...`. Путь вида `/Users/dmitry/...` в контейнере не
   работает: `/Users` не смонтирован.
3. Правки — в `$WF_ROOT/Client`, в том числе через контейнерные пути (`/workspace/client/CLAUDE.md`
   ведёт в тот же файл). Внешняя папка копий не держит: `.deepseek/` — зеркало, его обновляет конвертер,
   отдельных копий инструкций нет.
4. Правится только `$WF_ROOT/Client/CLAUDE.md`, остальные файлы инструкций — через него и конвертер:
   `AGENTS.md` и `.deepseek/instructions/project.md` генерируются командой
   `python3 .deepseek/scripts/convert.py export`. Корень конвертер берёт сам — на два уровня выше скрипта,
   то есть `/workspace/client`; `--repo $WF_ROOT/Client` нужен, только если запускать копию скрипта из
   другого места.
5. `$WF_ROOT` задаётся в окружении на каждой машине: в контейнере — `containerEnv` в
   `.devcontainer/devcontainer.json` (`/wf`, туда же смонтирована папка WF), на macOS —
   `export WF_ROOT="/Users/dmitry/Tank_agent-Claude-Deepseek-_WF"` в профиле оболочки. Абсолютные пути
   внутрь инструкций не записывать: в macOS путь начинается с `/Users/...`, в контейнере — с `/wf/...`.

# Язык общения

Все ответы ассистента пользователю должны быть на русском языке. Это касается ЛЮБЫХ агентов/
субагентов, запускаемых через `task` (Explore, general-purpose, Plan, кастомные агенты из
`.deepseek/agents/<команда>/*.md` и т.д.) — их финальные ответы пользователю тоже должны быть на русском.

# Явное указание личности: «Пользователь» или «ИИ»

Когда в тексте для человека (ответ ассистента, вопрос, документация, коммит, PR) или в передаче между
агентами речь идёт о личности, она называется прямо: «Пользователь» (живой человек, принимающий
решения) либо «ИИ» (ассистент: базовая сессия, любой агент системы, субагент). Неопределённые
местоимения «сам/сама/само/сами», «он/его/ему» без подлежащего, «кто-то» не использовать — по ним не
видно, о ком речь. Фразы, где «сам» выражает свойство объекта или кода («метод сам проверяет
предусловия», «сеттер сам увеличивает `styleID`»), правило не затрагивает. Подробно и для агентов —
`.deepseek/docs/agent-system-workflow.md#who-acts`.

# Проверка на противоречие с ранее принятыми решениями

Прежде чем зафиксировать ответ пользователя как окончательное решение (в коде, документации,
архитектуре) — проверь по памяти/документации этой же области, нет ли более раннего решения, которому
новое явно противоречит. Если есть — не принимай молча, переспроси: "Вы уверены? Ранее здесь было
решено X (причина: Y), новое решение этому противоречит — возможные последствия: Z." Продолжай только
после явного повторного подтверждения. Правило действует и для базовой сессии, и для всех агентов
многоагентной системы (см. `.deepseek/docs/agent-system-workflow.md`).

# Порядок вопросов пользователю

В один `AskUserQuestion` — только независимые вопросы. Если какой-то вариант ответа на один вопрос
снимает или меняет другой, этот другой задаётся отдельным вызовом после разбора ответа. Подробно и
для агентов — `.deepseek/docs/agent-system-workflow.md#question-order`.

# Движковый код в src/ee/ — не трогать

Не изменять файлы в `src/ee/` (движковый/библиотечный код: `TextBuilder`, `Layout`, `Slice9`, `Creator`
и т.д.) — ни ради рефакторинга, ни ради добавления удобных методов, даже если изменение обратно
совместимо и сократило бы код в вызывающем месте.

Любую логику, которая требует новых возможностей билдеров/утилит из `/ee/`, реализовывать локально в
вызывающем файле (например, напрямую работать с публичными полями `text.style.*`/`text.scale` в
обработчике события), а не расширять API `/ee/`-классов. Если без правки `/ee/` задачу решить нельзя —
сначала спросить пользователя.

# Никаких кастов к приватным полям — только public API

Запрещено использовать `as any` или `as unknown as { field: T }`, чтобы достучаться до приватных/
недекларированных в типах полей чужого класса (движка, библиотеки). Разрешено использовать только то,
что реально доступно как публичный field/метод/interface/class.

Если для задачи кажется, что нужен hack-каст к приватному/недекларированному полю — сначала
перепроверить, нет ли уже публичного пути получить тот же эффект (сеттер, публичный метод, геттер,
который сам форсирует нужный пересчёт/побочный эффект). Пример: вместо кастов к приватному `dirty` у
`PIXI.Text` достаточно было выставить публичное `TextStyle.wordWrapWidth` — его сеттер сам увеличивает
внутренний `styleID`, а `width`/`height` при чтении сами пересчитывают текст. Если публичного пути
действительно нет — не выкручиваться кастом, а спросить пользователя, как поступить (не менять
поведение вовсе, либо явно попросить разрешения расширить публичный API).

# Без развёрнутых комментариев в коде

Архитектурные пояснения (что за класс, почему так спроектировано, TODO) — в `.deepseek/docs/<тема>.md`,
не в `.ts`. В коде — либо без комментария, либо одна строка `// См. .deepseek/docs/<файл>.md#<якорь>`;
короткие однострочные `//` с неочевидным WHY на месте допустимы.

Ссылки на доки живут только на время разработки задачи. Когда пользователь сообщает о завершении
задачи, сначала финально обновляется и оптимизируется документация, затем все строки-ссылки
(`// См. ...md#...`, `ГДД #gdd-...`) удаляются из кода области целиком.

# Client — паковка ассетов (атласы, async/regular, raw-картинки)

Полная процедура (async per-id атласы через `Creator.spriteAsync`, обычные атласы через
`Creator.sprite`, raw-картинки, частые причины "картинка не показалась, ошибок нет") — в
`.deepseek/docs/asset-packaging.md`. Читай его целиком перед любой задачей на добавление
нового клиентского ассета — не пересказывай своими словами с искажениями, отсылай к нему
как к первоисточнику.

# Документ игрового дизайна (ГДД)

Бизнес-логика каждой области хранится в `.deepseek/docs/game-design/<область>-gdd.md` (одна копия на
client и server). Архитектурные документы ссылаются на его разделы (`gdd-<раздел>`). Правила
создания (запросить у пользователя файл с логикой, нет файла — примерное описание фичи), дополнения
(способ и содержимое — уточнять у пользователя) и проверки на противоречия/недостаточность —
`.deepseek/docs/agent-system-workflow.md#gdd`; читай этот раздел при любой задаче, где создаётся или
меняется архитектурная документация либо бизнес-логика области.

# Многоагентная система разработки (команды агентов)

В проекте есть иерархия команд агентов (`.deepseek/agents/<команда>/*.md`, подпапки `librarians/`, `analysts/`, `developers/`, `integration/`) для дев-задач: библиотекари → аналитики
→ разработчики, плюс команда интеграции client↔server. Полное описание (состав, порядок обращения,
стандарт документации, кросс-репо последовательность, правило "решение — всегда пользователю") — в
`.deepseek/docs/agent-system-workflow.md`, читай его целиком только когда решил(а) входить в пайплайн
(см. ниже) — не ради мелких задач. Состояние между сессиями (последняя ветка) — в служебном
`.deepseek/session_state.json` (НЕ часть memory-системы); у server свой независимый файл, ветки
трекаются раздельно.

## Проверка ветки/сессии при старте

В начале КАЖДОЙ по-настоящему новой сессии (свежий чат без предыдущего контекста в этом диалоге, а не
продолжение уже идущего разговора):

1. Прочитай `.deepseek/session_state.json` → `lastBranch`, сравни с текущей git-веткой этого репозитория
   (`client`). Если в этой же сессии затрагивается и `server` — аналогично сверь его собственный
   `.deepseek/session_state.json` с веткой `/workspace/server`.
2. Если текущая ветка ≠ `master` И текущая ветка ≠ `lastBranch` (для затронутого репозитория) — это
   точно новая задача на новой ветке: прежде чем продолжать, уточни у пользователя тип задачи:
   - разработка полностью новой фичи;
   - расширение уже имеющейся фичи/компонента;
   - исправление бага в существующем компоненте.
3. Обнови `lastBranch` в соответствующем `.deepseek/session_state.json` на текущую ветку.

Если сохранённая ветка совпадает с текущей — это продолжение той же работы, повторно тип задачи не
уточняй.

## Когда вообще входить в пайплайн команд

Пайплайн (библиотекари → аналитики → разработчики) — не для любого запроса. Порог срабатывания НЕ
определяй сам автоматически по размеру/типу задачи — спрашивай пользователя явно каждый раз, когда
запрос похож на дев-задачу в игровом коде (`src/` на клиенте, `game/` на сервере), но неочевидно,
разработка это, исследование или мелкая правка: "делать через пайплайн команд или разобраться
напрямую?" Однозначно НЕ спрашивай и работай напрямую (без пайплайна) для: мелких точечных правок
уровня опечатки/1 строки, вопросов "как что-то устроено" без изменения кода, работы над самой
инфраструктурой агентов (`.deepseek/*`, `CLAUDE.md`) — она не является предметом этой системы, а её
конфигурацией.

Входишь в пайплайн — читай `.deepseek/docs/agent-system-workflow.md` перед вызовом первого агента.

## Контроль расхода токенов

При входе в пайплайн — если в этой сессии ещё нет активной почасовой проверки (сверь `CronList`),
создай её: `CronCreate` с `cron: "17 * * * *"`, `recurring: true`, промпт — запустить
`python3 /workspace/client/.deepseek/scripts/token_usage_check.py 3600`, разобрать JSON:
- `idle: true` (за час не было ходов, кроме самой проверки, и работы субагентов) — пользователь
  отошёл: `CronList` → `CronDelete` этой задачи, ответ одной строкой "проверка токенов снята из-за
  простоя". При следующем сообщении пользователя пересоздать её (хук `token_check_resume_hook.py`
  напоминает об этом) — затем выполнить само сообщение.
- `flags` пуст — одна короткая строка "в норме", без деталей.
- `flags` непуст (ratio эффективного/нового input к output выше порога роли (10:1, у библиотекарей и integration — 25:1) у агента/сессии в целом, ИЛИ cache
  hit rate < 70% у агента с 2+ вызовами за час) — коротко перечислить, что превышено, и спросить через
  `AskUserQuestion`: оптимизировать сейчас или игнорировать. Без ответа пользователя дальше не
  действовать. Выбрано «оптимизировать» — новое правило сразу дописать одной строкой в
  `.deepseek/docs/agent-system-workflow.md#token-economy` (существующее — уточнить, не дублировать).

Ограничение: `CronCreate`-задачи живут только внутри текущей сессии (максимум 7 дней, исчезают при
закрытии чата) — при новой сессии, если снова входишь в пайплайн, создавай заново. Формулы метрик и
пороги — в самом скрипте (`.deepseek/scripts/token_usage_check.py`).

Симлинк `CLAUDE.md -> AGENTS.md` возможен только там, где `CLAUDE.md` нет (например, отдельный git

4. `git status -s CLAUDE.md .claude` — в диффе только ожидаемые правки задачи.
