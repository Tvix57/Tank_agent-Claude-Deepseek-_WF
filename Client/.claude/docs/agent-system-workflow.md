# Агентная система разработки — устройство ветки My_first_game

Устройство портировано из ветки `tank-docs` WF-папки (пайплайн «библиотекари → аналитики →
разработчики»), но пересобрано под этот проект и эту среду: только клиент, исполнение одной сессией,
ГДД — `CONCEPT.md`. Танковые агенты, документы и ГДД не переносились.

Читается ТОЛЬКО когда базовая сессия уже решила входить в пайплайн — не грузи ради мелких правок.

**Содержание:** [Отличия порта](#port) · [Состав команд](#teams) · [Порядок обращения](#order) ·
[Гарантированный признак области](#area-sign) · [Прямая связь](#direct-link) ·
[Ревью вместо integration](#integration) · [Передача между ролями](#handoff) ·
[Общие правила](#common-rules) · [ГДД](#gdd) · [Ветка ГДД](#gdd-flow) · [Стандарт документации](#doc-standard) ·

## 1. Отличия порта {#port}

| В `tank-docs` | Здесь |
|---|---|
| `Agent` tool, субагенты, `SendMessage` | недоступны: роль исполняет базовая сессия последовательно |
| `AskUserQuestion` | `ask_question`, один вопрос за вызов |
| `memory: local` (Claude Code) | файлы `.claude/memory/<роль>.md`, читаются по надобности |
| `CronCreate` контроля токенов | не применим: [#token-economy](#token-economy) |
| скиллы `humanizer`, `naming` | нет: правила проекта в этом файле, `CLAUDE.md`, `CONCEPT.md` |
| репозитории client и server, `integration-*` | только клиент: `integration` отсутствует, её функцию выполняет ревьюер фичи — сейчас `room-fix-reviewer` ([#integration](#integration)) |
| ГДД `.claude/docs/game-design/<область>-gdd.md` | `CONCEPT.md` (источник истины) + `concept-gdd/<раздел>/` |

Следствие: передача между ролями — не вызов, а фиксированный блок полей ([#handoff](#handoff)),
который базовая сессия переносит следующей роли дословно. У роли нет своего контекста: всё нужное
приходит в постановке задачи и в ссылках на файлы.

## 2. Состав команд {#teams}

`.claude/agents/` — контракты ролей, а не исполняемые субагенты. Файл роли читается перед её
исполнением.

**Лиды — общие на весь проект** (`agents/leads/`). Не принадлежат ни одной фиче: при появлении новой
фичи не пересоздаются, меняются только специалисты в `agents/features/<фича>/`:

- `librarian-lead` — диспетчер библиотекарей, владелец реестра документации компонентов;
- `analyst-lead` — маршрутизация аналитиков, сверка с `CONCEPT.md`, черновик архитектуры;
- `developer-lead` — маршрутизация разработчиков по слоям, итоговое саммари.

**ГДД** (отдельная ветка флоу, в общий пайплайн не входит — [#gdd-flow](#gdd-flow); роль общая, к
фиче не привязана):

- `gdd-writer` — собирает ГДД из папки концептов, делает выжимку по фичам, ставит ссылки на папки
  с изображениями и передаёт ГДД `analyst-lead`.

**Фича `room`** (`agents/features/room/`) — специалисты первой фичи проекта, работают под общими
лидами:

- `room-librarian-docs` — документация по комнатам, экрану базы, карте базы;
- `room-librarian-patterns-gamedev` — паттерны Cocos (префабы, атласы, ввод, сцена), практики
  мобильных игр. Общих TS-паттернов вне Cocos в проекте пока нет; появятся — специалист фичи;
- `room-analyst` — механика комнат: состояния, тиры, энергия, тепло, эффекты метра;
- `room-analyst-ui` — экран базы: этажи, плитки, карточка комнаты, префабы, ввод;
- `room-core-developer` — `core/` без `cc`: данные комнат, симуляция, карта базы, тесты;
- `room-ui-developer` — `game/ui`, префабы, сцена, ввод;
- `room-fix-reviewer` — ревью правок фичи: костыль между слоями, протечка движка, числа в коде.

Специалисты новой фичи создаются в `agents/features/<фича>/`; общие лиды и `gdd-writer` не
дублируются.

## 3. Порядок обращения {#order}

1. **Проверка входа.** Задача пришла папкой концептов — новая фича, по которой ГДД ещё нет, — это
   ветка ГДД: `gdd-writer` собирает ГДД и передаёт его `analyst-lead` ([#gdd-flow](#gdd-flow)),
   дальше шаг 3. Остальные задачи идут с шага 2.
2. **`librarian-lead`** — всегда первый в общем пайплайне. Вопрос: есть ли документация по области
   и по нужным паттернам. Документация нашлась — шаг 4.
3. **`analyst-lead`** — документации нет. Запрашивает ТЗ/референс, сверяет с `CONCEPT.md`,
   готовит черновик архитектуры и список специалистов фичи. Полный документ пишется один раз —
   после разработки, если область в этой задаче ещё изменится.
4. **`developer-lead`** — получает архитектуру или документацию, раздаёт по слоям, собирает
   саммари.
5. **Ревьюер фичи** — после разработки, если правка меняет границу `core/` ↔ `game/` или трогает
   бюджеты ([#integration](#integration)); сейчас это `room-fix-reviewer`, у новой фичи — свой.
6. Документация — через `analyst-lead` и `librarian-lead` в реестр, без пометки
   `auto-create`.

## 4. Гарантированный признак области {#area-sign}

Лиды (`librarian-lead`, `analyst-lead`, `developer-lead`) и `gdd-writer` — общие роли проекта: при
появлении новой фичи они не создаются заново. Новая роль — это специалист фичи в
`agents/features/<фича>/`. Спрашивать Пользователя перед созданием такого специалиста не нужно, если
у области есть структурный признак:

- собственный `id` в `assets/resources/config/rooms-layout.json` и состояние в `core/base/layout.ts`
  или `core/sim/rooms.ts` — специалист механики фичи `room`;
- собственная сцена/вид в `assets/scripts/game/ui` и собственные префабы в
  `assets/resources/prefabs` — специалист экрана фичи `room`;
- собственная папка `concept-gdd/<раздел>/` с файлом темы — дизайн-специалист фичи.

Признака нет (разовая правка, новый файл рядом с похожим) — вопрос Пользователю: специалист фичи
или работа без файла роли.

## 5. Прямая связь аналитик ↔ разработчик {#direct-link}

Пары фичи `room`: `room-core-developer` ↔ `room-analyst`, `room-ui-developer` ↔ `room-analyst-ui`.
Разработчик задаёт точечный вопрос напрямую, без пересказа всей задачи; ответ — какие разделы
документа обновлены. Читать документ целиком после ответа не нужно. У новой фичи пары создаются
вместе с её специалистами.

## 6. Ревью вместо integration {#integration}

Команды синхронизации client ↔ server в проекте нет: сервера нет, контрактов нет. Функция
`integration-fix-reviewer` сохранена как ревьюер фичи: сейчас `room-fix-reviewer`, для новой фичи
создаётся свой. Проверяет три вещи:

- не компенсирует ли один слой ошибку другого (фикс в `game/` вместо `core/` или наоборот);
- не протекла ли в `core/` зависимость от `cc`, времени кадра или ввода;
- не выведены ли числа баланса в код вместо конфига.

Находка «костыль» — задача возвращается `developer-lead` с полем `ПРИЧИНА`.

## 7. Передача между ролями {#handoff}

Поля, не связный текст. Постановка задачи: `ЗАДАЧА` / `ОБЛАСТЬ` / `ВХОД` (файлы, разделы, якоря) /
`ВЕРНУТЬ`. Ответ:

```
СДЕЛАНО: <пункты, по одному факту>
ФАЙЛЫ: <путь:строки — что изменено/где смотреть>
РЕШЕНИЯ: <решение — кто принял (Пользователь/ИИ), причина>
ПРИЧИНА: <файл:строка — почему; только у фикса бага, #root-cause-fix>
ОТКРЫТО: <риски, что не сделано; "нет", если пусто>
РИСКИ: <только разработчик: метод — риск — исправлено/вопрос, см. #code-risk-check>
ВОПРОСЫ: <вопросы Пользователю по #ask-relay; поле опускается, если вопросов нет>
```

Поля без содержания опускаются. Связный текст пишет только тот, кто отдаёт его человеку.

## 8. Общие правила {#common-rules}

Действуют для каждой роли и для базовой сессии.

- **Выбор между вариантами — Пользователю.** Роль не выбирает даже рекомендуемый вариант: вопрос
  идёт полем `ВОПРОСЫ`, базовая сессия задаёт его через `ask_question`. {#ask-relay}
- **Порядок вопросов.** В один вызов `ask_question` попадают только независимые вопросы. Зависимый
  (его существование или варианты меняются от ответа на другой) задаётся следующим вызовом после
  разбора ответа; роль помечает его «задать после ответа на п.N». {#question-order}
- **Кто именно действует.** «Пользователь» — человек, принимающий решения; «ИИ» — базовая сессия,
  роль, любой помощник. Имена ролей уточняют, какой именно ИИ действует. «Сам/он/кто-то» без
  подлежащего не применяются. {#who-acts}
- **Проверка на противоречие.** Прежде чем зафиксировать ответ как решение — сверить с
  `DECISIONS.md`, `CONCEPT.md` и документацией области. Явное противоречие не принимать молча:
  переспросить с прежним решением, причиной и последствиями.
- **Внешний источник недоступен.** Ссылка не открылась — пробовать raw/markdown-версию, соседнюю
  страницу официальной документации, поиск по названию метода. Все пути не сработали — пауза на
  этих данных, в ответ:
  `ИСТОЧНИК НЕДОСТУПЕН: <URL> — <шаг> — <ошибка дословно> — <что пробовал>`, `НЕ ХВАТАЕТ:` и
  `ВОПРОСЫ: как действовать дальше`. Недостающее не восполнять памятью модели. {#source-unavailable}
- **Экономия токенов.** Большие файлы (`CONCEPT.md`, `ROADMAP.md`, `DECISIONS.md`, архитектура
  области) читаются по `grep -n` и диапазонам строк, не целиком. Документ области — только нужные
  разделы по якорям. {#token-economy}
- **Имена.** Новые функции, поля и параметры — полные слова, не больше трёх слов, простой английский.
  Публичные члены классов в `core/` — `PascalCase`, приватные поля — `_camelCase`; это конвенция
  существующего кода, менять её в новой задаче не нужно. Сокращения в старом коде вне задачи не
  переименовываются. {#naming-rules}
- **Одно правило ГДД — одна функция.** Перед добавлением функции с бизнес-смыслом — поиск функции
  того же смысла в классе и рядом. Нашлась — использовать её. Дубль вне объёма задачи — сообщить,
  не чинить молча. {#gdd-function-mapping}
- **Без неявного порядка вызовов.** Переход состояния (флаги, жизненный цикл комнаты) — один метод
  у владельца состояния, а не последовательность шагов у вызывающего. {#no-implicit-order}
- **Исправление первопричины.** Баг: сначала назвать место, где значение становится неверным,
  отдельно от места, где виден симптом; чинить там, где возникает. `ПРИЧИНА:` в саммари.
  Проверка на `null` в месте падения вместо фикса источника — костыль. {#root-cause-fix}
- **Сначала убрать, потом добавить.** Новое требование встраивается так, будто оно было в области
  с самого начала. Новый флаг или ветка `if` по типу в нескольких местах, параметр ради одного
  вызывающего, копия класса с одним отличием — прикручивание: остановиться и вернуть вопрос.
  {#subtract-redesign}

## 9. ГДД и его дополнение {#gdd}

Источник истины по дизайну — `CONCEPT.md` в рабочем каталоге. Изменение баланса, систем или
структуры забега начинается с правки `CONCEPT.md`; тематические документы
`concept-gdd/<раздел>/<тема>.md` уточняют его и ссылаются на разделы. Код следует за документом.

- **Сверка.** Роль перед работой читает разделы `CONCEPT.md` по ссылке из темы (например §4.8 и
  §5.10 для комнат) и документ темы; расхождение с ними — не «новая фича», а дефект: вопрос
  Пользователю, не молчаливая правка.
- **Дополнение.** Новое правило всплыло по ходу работы — способ фиксации (новый раздел в
  `concept-gdd/<раздел>/<тема>.md`, правка существующего, запись в «Открытые вопросы», не
  фиксировать) уточняется у Пользователя. `CONCEPT.md` правит только Пользователь или ИИ по прямой
  задаче.
- **Журнал изменений** тематического документа: дата и одна строка «было → стало», только когда
  меняется уже описанная логика.
- **Недостаточность.** Пробел не додумывать: в «Открытые вопросы» и в `ВОПРОСЫ`. Чек-лист для
  комнат и экрана базы: граничные значения (0 и максимум метра, пустая очередь ремонта), повторное
  действие игрока, уход с экрана и возврат, пауза и ускорение симуляции, смерть героя посреди
  ремонта, разрушение комнаты при работах, смена забега, детерминизм при повторном прогоне.
  {#gdd-insufficiency}

### Отдельная ветка «концепты → ГДД → аналитик» {#gdd-flow}

Ветка включается только тогда, когда вход задачи — папка концептов Пользователя: описания фич,
наброски, изображения. Правка описанной области, баг или работа без папки концептов идут обычным
пайплайном ([#order](#order)), роль `gdd-writer` не вызывается. Ветка общая для всех фич: ГДД —
один документ, каких специалистов фичи он затрагивает, определяет `analyst-lead`.

1. **`gdd-writer`** получает от базовой сессии путь к папке концептов (`ВХОД`) и согласует с
   Пользователем структуру ГДД — список фич с якорями `{#gdd-<фича>}`.
2. Пишет ГДД в `concept-gdd/<раздел>/<тема>.md`: выжимка по фичам (правило, числа, состояния,
   граничные случаи), отдельный раздел на фичу, ссылки на папки изображений.
3. Передаёт ГДД `analyst-lead` полями `#handoff`: путь к документу, якоря фич, папки изображений,
   открытые вопросы. Дальше — обычный порядок: черновик архитектуры, разработка, ревью.
4. `CONCEPT.md` роль не правит; правило, которое должно попасть в источник истины, выносится в
   `ВОПРОСЫ` Пользователю.

Ссылки на изображения — только на существующие папки: `concept-art/<область>/` (концепт-арт),
`src/image/<область>/` (производственный арт от корня проекта), `Last_shift/assets/resources/atlas/`.
Папки нет — `нет` и вопрос Пользователю, вымышленный путь не пишется.

Пробелы и противоречия концептов — по `#gdd` и `#gdd-insufficiency`: в «Открытые вопросы» ГДД и в
`ВОПРОСЫ`, а не в молчаливую трактовку. Реестр компонентов роль не ведёт: строку обновляет
`librarian-lead`.

## 10. Стандарт документации компонента {#doc-standard}

Документ области (`.claude/docs/room-architecture.md` и подобные) обязан содержать:

1. Назначение и бизнес-логику.
2. Использованные референсы.
3. Использованные паттерны.
4. Полный список созданных и изменённых классов.
5. Якоря для навигации.
6. Оглавление по классам из п.4.
7. Для каждого класса — назначение, методы; у метода с бизнес-смыслом — какое правило
   `CONCEPT.md` он реализует (раздел и, если есть, якорь тематического документа).
8. Принятые компромиссы и уязвимости с причинами.
9. Связь с ГДД: в начале — ссылка на разделы `CONCEPT.md` и `concept-gdd/<раздел>/`; у каждого
   правила — ссылка на конкретный раздел.
10. Карта файлов компонента, два подраздела:
    - **прямое влияние** — реализуют компонент: модуль `core/`, вид `game/ui`, конфиг, префаб, тест;
    - **косвенное влияние** — где компонент подключается: `GameRoot`, `headless/loader.ts`, общий
      конфиг, общий атлас (с указанием, какая часть принадлежит компоненту), типы-зависимости.

    Мёртвые вхождения в карту не входят.

Критерий полноты: поиск по именам классов прямого влияния по `Last_shift/` — каждый файл с
вхождением стоит в одном из подразделов.

## 11. Самопроверка кода на риски {#code-risk-check}

Разработчик проходит список по каждому написанному или изменённому методу до передачи результата:

- **детерминизм** — в состоянии симуляции нет `float`, нет `Math.random()`, случайность только через
  `core/rng.ts` с явным сидом;
- **слой** — в `core/` нет импортов из `cc`, нет обращений к `director`, `view`, `input`;
- **тики, не кадры** — логика шагает по тику 250 мс, падение fps не меняет результат;
- **числа в данных** — цена, тепло, эффекты взяты из `assets/resources/config/*.json`;
- **бюджеты** — тик ≤ 2 мс, draw calls ≤ 60, сборка < 30 МБ;
- **идемпотентность** — повторное действие игрока (тап по плите, повторный запуск ремонта) не даёт
  второго эффекта у владельца состояния;
- **тесты** — новое поведение закрыто тестом в `Last_shift/tests`, прогон `npm test` и
  `npm run typecheck` пройден.

Итог — поле `РИСКИ`. Ссылки на `#root-cause-fix` и `#subtract-redesign` — в
[#common-rules](#common-rules).

## 12. Память и реестр {#memory}

- Реестр документации компонентов — `.claude/docs/component-docs-registry.md`, владелец
  `librarian-lead`.
- Личная память ролей — `.claude/memory/<роль>.md`; есть у специалистов, у общих лидов её нет:
  правила записи, лимиты и когда читать — `.claude/docs/agent-memory.md`.
- Ход задачи никуда не записывается: он живёт в передаче ([#handoff](#handoff)) и в документации
  области.
