Решения пользователя 2026-10-15 при документировании аэродрома и боя:
- ТЗ «Страница аэродрома» считается реализованным: ГДД аэродрома пишется по коду, отменённые правила ТЗ — в журнал.
- ТЗ «Воздушный бой» и «Новые параметры самолётов» — ЦЕЛЬ, ещё не реализовано: ГДД боя по ТЗ, отличия кода —
  нереализованные правила. Исключение: выбор цели самолётом — как в коде (таблицы приоритета).
- Наземный бой танков в ГДД боя пока не вносить: пользователь пришлёт отдельное ТЗ.
- Battlefield (PvP в реальном времени, лиги, рейтинг; BattlefieldUserComponent, часть пакета model.battle) —
  отдельная область, анализ позже. Документа и агентов нет.
- Нумерация: слот самолёта N из ТЗ = позиция 8−N в коде.
- Стык детерминизма client↔server разобран integration-lead 2026-10-17 (сервер пересимулирует только win=true по
  сохранённым battleData; в проде расхождение видно игроку как «победил, уровень не вырос», ответ ok без награды).
  Пользователь 2026-10-17 отложил все решения:
  - Д1 (высокий): замена танка в бою только на клиенте (HomeScreen.ts:1025 → Battle.replaceTank → UnitTank.init
    тратит ГСЧ); бьёт по основному циклу (призыв/автозамена). Варианты: А журнал замен клиент→сервер и replaceTank в
    серверном движке с тем же расходом ГСЧ (рекомендация); Б новый танк со следующего боя (меняет campaign-gdd
    #gdd-battlefield). Решение отложено.
  - Д2 (средний): ничья — клиент не завершает бой (Battle.ts:412–427), бой зависает до перезахода; сервер отдаёт
    победу игроку как в ГДД. Исправление только на клиенте: нет живых → победитель fighters[0].
  - Д3 (средний): урон при броне < 0 — float сервер vs double клиент, 196 расхождений на 1. Варианты: А целочисленная
    формула floor(damage*m4*(100+|dur|)/400) на обеих сторонах (меняет сервер в 104 случаях); Б Math.fround на клиенте.
    Решение отложено.
  - Д4, Д5, server п.16 — низкий, эффекта нет (буст в кампании = 0; туториал без эмуляции; событие на тик позже).
  - server п.2 наблюдаемость: (а) признак verified в ответе, (б) контрольная сумма и лог несовпадений — спросить после
    решения по Д1.
  - Для отложенных правил ТЗ: только целочисленная арифметика; бросок промаха в одном месте цепочки на обеих сторонах;
    поле манёвренности добавить в DTO обеих сторон; времена передавать в BattleData без клиентских дефолтов; номер
    версии движка в BattleData; правка правил боя всегда парой.

**Why:** чтобы при следующих задачах не путать статус ТЗ двух областей и не потерять отложенные шаги.
**How to apply:** при задаче по бою или Battlefield напомнить про ожидаемое ТЗ наземного боя, анализ Battlefield и
стык детерминизма. Доки: client battle-architecture.md, air-battle-architecture.md; server battle-architecture.md;
aerodrome-architecture.md с обеих сторон.
