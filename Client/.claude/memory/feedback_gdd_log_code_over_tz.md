Если при составлении ГДД пользователь выбирает «как в коде» там, где ТЗ говорит иначе, это фиксируется в
`#gdd-log` строкой «<дата> — #раздел: по ТЗ X → Y (как в коде, решение пользователя)». Правило действует и при
создании ГДД, хотя регламент #gdd разрешает журнал только для изменения уже описанной логики. Пробелы ТЗ, закрытые
«как в коде», в журнал не идут: ТЗ там ничего не говорило.

**Why:** пользователь 2026-10-15 попросил дополнить журналы уже созданных ГДД (AirDrop, достижения, сборка, квесты)
такими записями: должно быть видно, что расхождение с ТЗ сознательное. До этого (тоже 2026-10-15) он решил регламент
не менять и решать по каждому ГДД, поэтому формат строк зависит от ГДД: в кампании — одна сводная строка по его
выбору, в остальных — по строке на раздел.
**How to apply:** при каждом новом ГДД и при дополнении существующего (ближайший — train-gdd.md по «Механике кора»)
сразу давать аналитику указание записать такие решения в журнал. Если библиотекарь возражает со ссылкой на регламент,
ссылаться на это решение. Связано: [[feedback-gdd-function-mapping]].
