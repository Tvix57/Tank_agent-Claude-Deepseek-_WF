Не использовать рефлексию (`Class.forName(...)`, `.newInstance()`,
`getDeclaredConstructor()` и т.п.) в серверном Java-коде
(`/workspace/server`) — это правило по умолчанию, применять всегда, а не
только к текущей задаче с коллекциями.

**Почему:** пользователь явно это запретил при обсуждении дизайна фабрики
коллекционных предметов (`ItemFactory`/`CollectionItem.newFromDocument`), в
момент, когда я предлагал рефлексию как способ добиться "нулевой" регистрации
новых подклассов (создание по сохранённому в документе имени класса вместо
явной `Supplier`-мапы). Рефлексия хрупкая к переименованиям/переносам классов
(что как раз произошло в этой же сессии — классы переезжали между пакетами) и
не в стиле остального кода, где везде явные `ImmutableMap<Enum, Supplier<T>>`
(см. `ItemFactory`, `EnumValues`-паттерн для `ItemType`/`CollectionSection`).

**Как применять:** если для новой задачи кажется, что рефлексия сократила бы
код (динамическая фабрика, автогенерация, сериализация по имени класса и
т.п.) — не предлагать её как реализуемый вариант по умолчанию. Можно упомянуть
как теоретическую альтернативу с явной пометкой "не используем по правилу
проекта", но не реализовывать без отдельного явного разрешения пользователя.
Вместо неё — явные `enum` + `ImmutableMap<Enum, Supplier<T>>`-фабрики.

**Обновление**: сам пример с `CollectionItemKind` + `CollectionItem.
newFromDocument` тоже был отклонён (отдельная причина — persisted
поле-дискриминатор избыточно, см. [[client_collection_section_hierarchy_draft]]),
но правило "без рефлексии" остаётся в силе независимо от этого — см. также
`/workspace/server/.claude/docs/collections-architecture.md` (пункт "Правило проекта:
без рефлексии").
