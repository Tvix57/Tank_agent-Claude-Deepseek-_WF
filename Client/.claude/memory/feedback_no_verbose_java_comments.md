В серверном Java-коде (`/workspace/server`) не писать развёрнутые
многострочные javadoc-комментарии к классам и методам (`/** ... */` с
объяснением архитектуры/решений/рационале). Это правило по умолчанию для
любой будущей задачи на сервере, не только для коллекций.

**Почему:** пользователь явно попросил убрать такие комментарии из новых
классов иерархии `Collection`/`CollectionItem` — они загромождают код. Вместо
этого нужен отдельный markdown-файл с документацией, который можно прочитать
отдельно от кода и при необходимости выгрузить на внешний ресурс.

**Как применять:**
- В коде — либо вообще без комментария, либо (когда нужна отсылка) короткая
  однострочная пометка вида `// См. .claude/docs/<файл>.md`.
- Развёрнутое описание (что за класс/иерархия, почему так спроектировано,
  какие есть TODO/открытые вопросы) — в `.claude/docs/<тема>.md` (не во внешней
  папке `docs/` в корне репозитория — такой быть не должно, это зона
  библиотекаря по документации, см. [[feedback_no_git_dependency_tooling_files]])
  соответствующего репозитория (см. пример:
  `/workspace/server/.claude/docs/collections-architecture.md`).
- Это НЕ отменяет обычные короткие однострочные `//`-комментарии там, где они
  объясняют неочевидный WHY (существующий стиль кода такие уже использует,
  трогать их не нужно) — правило именно про РАЗВЁРНУТЫЕ/многострочные
  пояснения к классам и методам.

**Обновление**: правило рецидивировало в ходе интенсивного рефакторинга
`CollectionSectionType`/`AlbumsSectionType`/`ExperimentalTanksSectionType`/
`CollectionUserComponent` — при каждой новой правке архитектуры я снова
добавлял многострочные пояснения "почему так" прямо к методам вместо того,
чтобы сразу переносить это в `.claude/docs/collections-architecture.md`. Пользователь
поправил повторно. Вывод: при любом Java-рефакторинге на сервере, где меняется
архитектура/распределение ответственности — по умолчанию писать объяснение
СРАЗУ в docs/*.md, а в коде оставлять максимум `// См. docs/<файл>.md`, даже
если объяснение кажется коротким и полезным прямо на месте.

**Второй рецидив** (тот же файл `ExperimentalTanksSectionType.java`, серия
точечных правок в рамках одной сессии): комментарии снова разрослись до
6-8 строк на метод (`claimSetReward`/`buildSetCompletedJSON`/`findRank`/
`findRankCollectionId`). Пользователь поправил третий раз и добавил новое
требование по процессу:

- Проверять код на разросшиеся комментарии и подрезать их нужно **точечно
  через `grep -n "^\s*//" <файл>`**, а НЕ через полное чтение файла (`Read`)
  каждый раз — это экономит токены при повторных проверках одного и того же
  файла в рамках одной сессии. Найденные через grep строки дают достаточно
  контекста для точного `Edit` (old_string/new_string), полное чтение файла
  для этого не нужно.
- Это общий принцип для любых точечных grep-проверок/правок на сервере и
  клиенте, не только для комментариев — если задача сводится к "найти и
  поправить конкретные вхождения", предпочитать `grep`/`Bash` вместо `Read`
  всего файла, особенно если файл уже большой или проверяется повторно.

**2026-09-23 — то же самое на клиенте:** правило "не писать развёрнутые комментарии,
выносить в docs" распространено и на клиентский `.ts` (не только серверный Java) —
см. отдельную запись [[feedback_no_verbose_ts_comments]] (свой список файлов/целевой
документ `collections-architecture.md` на стороне клиента).

**2026-09-23 — найдена и устранена корневая причина рецидивов**: правило жило ТОЛЬКО в
этой клиентской памяти, а 4 серверных агентских файла (`server-developer-collections.md`,
`server-developer-lead.md`, `server-developer-db-persistence.md`,
`server-analyst-collections.md`) ссылались на него как "см. `CLAUDE.md`" или прямо "см.
клиентскую память" — но у серверных субагентов нет доступа к клиентской памяти, а в
`/workspace/server/CLAUDE.md` само правило текстом отсутствовало. Ссылка была битая, поэтому
субагенты не видели правило заново при каждом новом вызове. Исправлено: правило (и парное
"без рефлексии", та же проблема) добавлено ТЕКСТОМ прямо в `/workspace/server/CLAUDE.md`
(разделы "Без рефлексии"/"Без развёрнутых комментариев в коде"), ссылка в
`server-developer-db-persistence.md` на клиентскую память заменена на `CLAUDE.md`. Вывод на
будущее: правило, которое должны соблюдать СЕРВЕРНЫЕ субагенты, обязано жить текстом в
`/workspace/server/CLAUDE.md` (или в файле самого агента) — клиентская память для них не
видна в принципе, ссылка на неё гарантированно битая. Не проверено: аналогичная ли ситуация
на клиенте (`feedback_no_verbose_ts_comments` — тоже только в памяти, в `/workspace/client/CLAUDE.md`
текста правила нет) — риск того же рецидива, но пользователь не просил чинить сейчас.

**2026-10-13 — ссылки на доки только на время разработки** (решение пользователя при завершении
коллекций): строки `// См. ...md#якорь` / `ГДД #gdd-...` нужны, пока задача в работе. Когда
пользователь сообщает о завершении задачи: 1) финальное обновление и оптимизация документации
(аналитиками области), 2) удалить все строки-ссылки на доки из кода области целиком (вместе с
пояснением в той же строке; прочие короткие `//` WHY не трогать). Текст правила — в
`client/CLAUDE.md` и `server/CLAUDE.md` («Без развёрнутых комментариев в коде»).
