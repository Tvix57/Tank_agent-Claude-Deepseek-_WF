## Ключ запроса от клиента {#web-idempotency-key}

- **Задача:** защита выдачи награды при открытии лутбокса от двойного нажатия, повтора после обрыва сети, двух вкладок.
- **Ключевые слова:** idempotency key, request id, UUID, повтор запроса, двойное нажатие, лутбокс, retry, лутбокс-награда.
- **Рекомендация:** клиент генерирует высокоэнтропийный ключ (UUID v4) один раз на логическое действие «открыть» и повторяет его при каждом ретрае. Сервер запоминает ключ и результат первого выполнения; повтор с тем же ключом возвращает сохранённый результат, а не выполняет заново. Тот же ключ с другими параметрами — ошибка. Параллельный повтор, пока первый выполняется, — отказ/конфликт, не второе выполнение. Хранить ключи не меньше 24 ч, затем чистить.
- **Плюсы:** закрывает все три сценария, включая потерянный ответ (клиент получает ту же награду, что выпала); общепринятая схема (Stripe и др.); не зависит от формы состояния объекта.
- **Минусы:** нужно хранилище ключей и их очистка; клиент обязан правильно переиспользовать ключ (новый ключ на каждый клик защиты не даёт); ключ не выводить хэшем от тела запроса.
- **Применимость к проекту:** в акторной модели запросы игрока идут последовательно, поэтому гонки «проверил-записал» внутри одного игрока нет; ключи можно держать в состоянии игрока (ограниченный кольцевой набор последних N) и сохранять вместе с ним. Два процесса/сервера на одного игрока актором не закрываются — см. раздел про уникальный индекс. Правки клиента нужны (генерация ключа). Конфликтов с CLAUDE.md не найдено.
- **Источники:** https://docs.stripe.com/api/idempotent_requests — 2026-10-27; https://bugnet.io/blog/how-to-build-an-idempotent-reward-granting-system — 2026-10-27 (блог, вес низкий).
- **Статус:** не применялось.

## Состояние «открыт/выдан» в объекте {#web-opened-state-flag}

- **Задача:** то же; без участия клиента в защите.
- **Ключевые слова:** state machine, флаг opened, статус лутбокса, удаление предмета, атомарная смена состояния, идемпотентность по состоянию.
- **Рекомендация:** (общая инженерная практика, в найденных источниках прямо не описана) сам лутбокс переходит в состояние «открыт»/удаляется из сумки в той же атомарной операции, что и начисление награды; повтор находит лутбокс уже открытым и не выдаёт повторно. Результат броска сохраняется в объекте, чтобы повтор мог вернуть ту же награду.
- **Плюсы:** не нужен ключ и клиентские правки; естественно для акторной модели (один поток на игрока, смена состояния и начисление без гонок); нет отдельного хранилища.
- **Минусы:** при потере ответа клиент не узнает, что выпало, если результат не сохранён; не различает «повтор» и «второй лутбокс того же вида» (если стек количеством); между сохранениями в БД возможен откат состояния при сбое сервера (награда в памяти есть, в БД нет, или наоборот).
- **Применимость к проекту:** подходит как база для актора; надёжность определяется границей сохранения состояния в БД (периодическое сохранение) — награда и пометка «открыт» должны попадать в один документ/одну запись.
- **Источники:** вывод из https://docs.stripe.com/api/idempotent_requests и https://bugnet.io/blog/how-to-prevent-duplicate-reward-grants-from-retries — 2026-10-27 (прямого описания паттерна нет, частично мнение библиотекаря).
- **Статус:** не применялось.

## Уникальный индекс по операции в MongoDB {#web-unique-index-operation}

- **Задача:** гарантировать «не более одной выдачи на операцию» на уровне БД, независимо от процессов/вкладок/серверов.
- **Ключевые слова:** MongoDB, unique index, E11000, duplicate key, upsert, идемпотентность, claim, атомарная вставка.
- **Рекомендация:** отдельная коллекция операций с уникальным индексом (например, `playerId + operationId`). Перед выдачей — атомарная вставка записи-«заявки»; E11000 на повторе трактовать как «уже выполнено» (прочитать сохранённый результат), а не как сбой. Читать-потом-писать небезопасно — только одна атомарная вставка до начала работы. Исход записывать вместе с изменением награды (в одной транзакции, если нужна согласованность).
- **Плюсы:** жёсткая гарантия на уровне БД, работает при нескольких экземплярах сервера и вкладках; простая реализация; запись-журнал заодно даёт аудит.
- **Минусы:** лишняя запись в БД на каждое открытие; между вставкой заявки и выдачей возможен сбой — нужна обработка «заявка есть, результата нет»; транзакции Mongo требуют replica set; описание поведения уникальных индексов внутри транзакций в найденном источнике — форумное сообщение, проверять по документации MongoDB; чистка старых записей (TTL-индекс).
- **Применимость к проекту:** при сохранении состояния «периодически» отдельная запись сразу в БД ломает модель «состояние в памяти» — это граница персистентности (по правилам проекта решает пользователь). Нужна миграция/создание индекса сразу при внедрении.
- **Источники:** https://oneuptime.com/blog/post/2026-03-31-mongodb-how-to-handle-duplicate-key-errors-on-unique-indexes-in-mong/markdown — 2026-10-27 (блог); https://www.mongodb.com/community/forums/t/unique-index-transaction-e11000-duplicate-key-error-inside-transaction/132344 — 2026-10-27 (форум); https://bugnet.io/blog/how-to-prevent-duplicate-reward-grants-from-retries — 2026-10-27.
- **Статус:** не применялось.

## Журнал выдачи / outbox {#web-grant-journal-outbox}

- **Задача:** надёжно довести выдачу награды до побочных эффектов (инвентарь, статистика, уведомления, push) без потерь и дублей.
- **Ключевые слова:** transactional outbox, журнал выдачи, ledger, at-least-once, идемпотентный потребитель, relay.
- **Рекомендация:** запись о выдаче (outbox/журнал) пишется в той же транзакции БД, что и изменение состояния; отдельный обработчик (relay) публикует/применяет её. Доставка «минимум один раз» — потребитель обязан быть идемпотентным (хранить id обработанных записей).
- **Плюсы:** нет потери эффекта при сбое между шагами; порядок сохраняется; аудит и возможность сверки/отката поддержкой.
- **Минусы:** самый тяжёлый вариант (relay, очистка, мониторинг); без идемпотентного потребителя дубли всё равно возможны; нужен транзакционный write (replica set); для одного модуля с одной БД избыточен.
- **Применимость к проекту:** вероятно избыточен для одной выдачи в сумку игрока; имеет смысл, только если выдача затрагивает несколько хранилищ/сервисов. Рекомендация носит внешний характер, конвенциям проекта не противоречит, но требует решения по границе персистентности.
- **Источники:** https://microservices.io/patterns/data/transactional-outbox.html — 2026-10-27.
- **Статус:** не применялось.
