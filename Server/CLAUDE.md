# Корень инструкций — папка WF вне контейнера

Все файлы инструкций проекта (этот файл, `AGENTS.md` и раскладка агентов: команды, скиллы, документация,
память) живут в одной папке WF **вне контейнера** и правятся только там: у сервера это `$WF_ROOT/Server`.
Рабочий каталог `/workspace/server` подключён к ней симлинками `CLAUDE.md`, `AGENTS.md` и `.claude/`.

1. Проверка: `echo $WF_ROOT; ls -l /workspace/server/CLAUDE.md /workspace/server/AGENTS.md
   /workspace/server/.claude /workspace/server/.deepseek` — все четыре ссылки ведут в `$WF_ROOT/Server`.
   Переменная не задана, ссылки битые или указывают мимо папки WF — остановиться, ничего не создавать и
   не перезаписывать рядом (копия в контейнере теряется при пересоздании и расходится с источником),
   спросить Пользователя.
2. Пути в этом файле записаны относительно папки инструкций сервера `$WF_ROOT/Server`: `.claude/docs/...`
   читается как `$WF_ROOT/Server/.claude/docs/...`. Путь вида `/Users/dmitry/...` в контейнере не
   работает: `/Users` не смонтирован.
3. Правки — в `$WF_ROOT/Server`, в том числе через контейнерные пути (`/workspace/server/CLAUDE.md`
   ведёт в тот же файл). Внешняя папка копий не держит: `.deepseek/` — зеркало, его обновляет конвертер,
   отдельных копий инструкций нет.
4. Правится только `$WF_ROOT/Server/CLAUDE.md`, остальные файлы инструкций — через него и конвертер:
   `AGENTS.md` и `.deepseek/instructions/project.md` генерируются командой
   `python3 .deepseek/scripts/convert.py export`. Корень конвертер берёт сам — на два уровня выше скрипта,
   то есть `/workspace/server`; `--repo $WF_ROOT/Server` нужен, только если запускать копию скрипта из
   другого места.
5. `$WF_ROOT` задаётся в окружении на каждой машине: в контейнере — `containerEnv` в
   `.devcontainer/devcontainer.json` (`/wf`, туда же смонтирована папка WF), на macOS —
   `export WF_ROOT="/Users/dmitry/Tank_agent-Claude-Deepseek-_WF"` в профиле оболочки. Абсолютные пути
   внутрь инструкций не записывать: в macOS путь начинается с `/Users/...`, в контейнере — с `/wf/...`.
# Язык общения

Все ответы ассистента пользователю должны быть на русском языке. Это касается ЛЮБЫХ агентов/
субагентов, запускаемых через Agent tool (Explore, general-purpose, Plan, кастомные агенты из
`.claude/agents/<команда>/*.md` и т.д.) — их финальные ответы пользователю тоже должны быть на русском.

# Проверка на противоречие с ранее принятыми решениями

Прежде чем зафиксировать ответ пользователя как окончательное решение (в коде, документации,
архитектуре) — проверь по памяти/документации
этой же области, нет ли более раннего решения, которому новое явно противоречит. Если есть — не
принимай молча, переспроси: "Вы уверены? Ранее здесь было решено X (причина: Y), новое решение этому
противоречит — возможные последствия: Z." Продолжай только после явного повторного подтверждения.
Правило действует и для базовой сессии, и для всех агентов многоагентной системы (см.
`.claude/docs/agent-system-workflow.md`).

# Порядок вопросов пользователю

В один `AskUserQuestion` — только независимые вопросы. Если какой-то вариант ответа на один вопрос
снимает или меняет другой, этот другой задаётся отдельным вызовом после разбора ответа. Подробно и
для агентов — `.claude/docs/agent-system-workflow.md#question-order`.

# Без рефлексии

Не использовать рефлексию (`Class.getDeclaredField`/`setAccessible`/`Method.invoke` и т.п.) нигде в
серверном коде — ни для персистентности, ни для полиморфного конструирования по типу. Различение по
типу/маршрутизация — через обычный `enum`/`instanceof`/явный dispatch-параметр (например, `collectionId`
→ `CollectionsData.section`), а не через рефлексию.

# Баланс всегда считается верным

Данные баланса (Google-таблица → `balance.json` → `Balance`) — источник истины, а не входные данные,
которые код вправе чем-то заменить. Отсутствующий лист, отсутствующие обязательные данные в строке или
значение вне шкалы — ошибка, останавливающая импорт/сборку баланса с сообщением, где именно ошибка
(лист, id строки, поле).

Запрещено: необязательные листы (`optJSONArray` и подстановка пустого массива вместо данных), значения
по умолчанию вместо данных баланса, `try/catch` вокруг чтения баланса «чтобы сервер поднялся»,
молчаливый пропуск листа или строки при импорте. Незаполненный баланс — это дефект таблицы, он
правится Пользователем в таблице; заглушка в коде вместо данных баланса — только по явной просьбе
Пользователя.

# Без развёрнутых комментариев в коде

Не писать развёрнутые многострочные комментарии (включая `/** ... */`) к классам/методам,
объясняющие архитектуру, рационале или процесс принятия решения — они загромождают код и быстро
устаревают. Архитектурные пояснения (что за класс/механизм, почему так спроектировано, открытые
TODO) — только в `.claude/docs/<тема>.md`. В коде — либо совсем без комментария, либо короткая
однострочная пометка `// См. .claude/docs/<файл>.md#<якорь>`.

Такие ссылки живут только на время разработки задачи. Когда пользователь сообщает о завершении
задачи, сначала финально обновляется и оптимизируется документация, затем все строки-ссылки на доки
(`// См. ...md#...`, `ГДД #gdd-...`) удаляются из кода области целиком. Связь «класс → раздел»
после этого держит сама документация (поиск по имени класса).

Обычные короткие однострочные `//`-комментарии, объясняющие неочевидный WHY прямо на месте (не
пересказ архитектуры), это правило не запрещает. Запрещены именно многострочные пояснения —
в том числе двух-трёхстрочные, если они описывают логику/причину, а не просто отсылают к документу.

# Индексы MongoDB — миграция сразу

Новая Mongo-коллекция (новый `*Dao`) или новый фильтр запроса по полю без индекса — JSON-миграция
индекса (`game/src/main/resources/migrations/<timestamp_мс>_<имя>.json`) создаётся в ТОМ ЖЕ
изменении, не отдельным шагом потом. Формат, порядок и риски уникальных индексов — раздел «Индексы и
миграции» в `.claude/agents/developers/server-developer-db-persistence.md`.

# Документ игрового дизайна (ГДД)

Бизнес-логика каждой области хранится в `/workspace/client/.claude/docs/game-design/<область>-gdd.md` (одна копия на
client и server, на сервере своей не заводить). Архитектурные документы ссылаются на его разделы (`#gdd-<раздел>`). Правила
создания (запросить у пользователя файл с логикой, нет файла — примерное описание фичи), дополнения
(способ и содержимое — уточнять у пользователя) и проверки на противоречия/недостаточность —
`/workspace/client/.claude/docs/agent-system-workflow.md#gdd`; читай этот раздел при любой задаче, где создаётся или
меняется архитектурная документация либо бизнес-логика области.

# Многоагентная система разработки (команды агентов)

В проекте есть иерархия команд агентов (`.claude/agents/<команда>/*.md`, подпапки `librarians/`, `analysts/`, `developers/`, `integration/`) для дев-задач: библиотекари →
аналитики → разработчики, плюс команда интеграции client↔server. Полное описание (состав, порядок
обращения, стандарт документации, кросс-репо последовательность, правило "решение — всегда
пользователю") — в `.claude/docs/agent-system-workflow.md`, читай его целиком только когда решил(а)
входить в пайплайн — не ради мелких задач. У server своё `.claude/session_state.json` (не общее с
client) — ветку трекай отдельно; свои независимые копии агентов-лидов; `integration-*` — общая с
client, идентичные копии.

## Проверка ветки/сессии при старте

В начале КАЖДОЙ по-настоящему новой сессии (свежий чат без предыдущего контекста в этом диалоге, а не
продолжение уже идущего разговора):

1. Прочитай `.claude/session_state.json` (в server) → `lastBranch`, сравни с текущей git-веткой
   репозитория `/workspace/server`. Если в этой же сессии затрагивается и `client` — аналогично сверь
   его собственный `.claude/session_state.json` с веткой `/workspace/client`.
2. Если текущая ветка ≠ `master` И текущая ветка ≠ `lastBranch` (для затронутого репозитория) — уточни
   у пользователя тип задачи, прежде чем продолжать: разработка новой фичи / расширение имеющейся /
   исправление бага.
3. Обнови `lastBranch` в соответствующем `.claude/session_state.json` на текущую ветку.

Если работа в этой сессии идёт одновременно и в client, и в server — проверка веток и уточнение типа
задачи делаются один раз для задачи в целом, а не отдельно на каждый репозиторий.

## Когда вообще входить в пайплайн команд

Тот же принцип, что в `/workspace/client/CLAUDE.md`: порог срабатывания НЕ определяй сам автоматически
— спрашивай пользователя явно, когда запрос похож на дев-задачу в `game/`, но неочевидно, разработка
это, исследование или мелкая правка: "делать через пайплайн команд или разобраться напрямую?"
Однозначно НЕ спрашивай и работай напрямую для: точечных правок уровня опечатки/1 строки, вопросов "как
что-то устроено" без изменения кода, работы над самой инфраструктурой агентов (`.claude/*`,
`CLAUDE.md`).

Входишь в пайплайн — читай `.claude/docs/agent-system-workflow.md` перед вызовом первого агента.

## Контроль расхода токенов

При входе в пайплайн — если в этой сессии ещё нет активной почасовой проверки (сверь `CronList`),
создай её: `CronCreate` с `cron: "17 * * * *"`, `recurring: true`, промпт — запустить
`python3 /workspace/server/.claude/scripts/token_usage_check.py 3600`, разобрать JSON:
- `flags` пуст — одна короткая строка "в норме", без деталей.
- `flags` непуст (ratio эффективного/нового input к output > 10:1 у агента/сессии в целом, ИЛИ cache
  hit rate < 70% у агента с 2+ вызовами за час) — коротко перечислить, что превышено, и спросить через
  `AskUserQuestion`: оптимизировать сейчас или игнорировать. Без ответа пользователя дальше не
  действовать. Выбрано «оптимизировать» — новое правило сразу дописать одной строкой в
  `/workspace/client/.claude/docs/agent-system-workflow.md#token-economy` (существующее — уточнить, не дублировать).

Ограничение: `CronCreate`-задачи живут только внутри текущей сессии (максимум 7 дней, исчезают при
закрытии чата) — при новой сессии, если снова входишь в пайплайн, создавай заново. Формулы метрик и
пороги — в самом скрипте (`.claude/scripts/token_usage_check.py`). При смешанной client+server сессии
достаточно одной проверки (см. `/workspace/client/CLAUDE.md`) — не создавай вторую поверх неё.
